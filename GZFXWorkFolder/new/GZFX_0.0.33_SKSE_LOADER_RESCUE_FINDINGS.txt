GZFX 0.0.33 SKSE LOADER RESCUE — FIELD FINDINGS
Date: 2026-11-05

OWNER FIELD RESULT
The first real-Skyrim field test after 0.0.32 failed before any usable GZFX runtime behavior:
- GZFX menu/hotkeys did not work in game;
- no GZFX runtime/output folder was created under the normal Windows Documents/My Games/Skyrim Special Edition path;
- SKSE, Address Library, and GZFX were installed/enabled by the owner.

FIELD CLASSIFICATION
This is not a renderer-quality failure.
This is not a menu-only failure.
No GZFX runtime output means the field session did not reach a healthy SKSEPlugin_Load/runtime initialization path.

SKSE ABI / COMPATIBILITY CHECK
The custom GZFX SKSE ABI was rechecked against official ianpatt/skse64 source at the current 2.3.1 / 1.7.104 source state:
- SKSEInterface field layout matches;
- Messaging interface v2 layout matches;
- Trampoline interface v1 layout matches;
- SKSEPluginVersionData size/layout matches 0x350 / 848 bytes;
- runtime constant 1.7.104 packs to 0x01070680;
- SKSE 2.3.1 release index is 75;
- explicit compatibleVersions={1.7.104,0} is accepted by SKSE compatibility logic;
- minimum SKSE 2.3.1 is not greater than the matching runtime's PACKED_SKSE_VERSION.

Therefore the field failure is NOT presently explained by an obviously malformed SKSE ABI or version declaration.

UNVALIDATED REAL-RUNTIME RISK 1 — PRELOAD IAT SURGERY
0.0.31/0.0.32 SKSEPlugin_Preload executes:
    ArmEarlyGraphicsBootstrap()
      -> ArmD3D11LifecycleProbe()
         -> parse SkyrimSE.exe PE import table
         -> VirtualProtect and rewrite D3D11/DXGI IAT slots

SKSE upstream explicitly states game/SKSE functionality is limited during Preload.

The CI skse_single_dll_frontdoor harness does NOT execute against SkyrimSE.exe.
It performs the same operation against the CI harness executable's ordinary import table.
Thus CI did not prove that pre-global-initializer IAT rewriting is safe against the real 1.7.104 Skyrim executable.

This is the first real field attempt of that migration and it failed before GZFX runtime output.

UNVALIDATED REAL-RUNTIME RISK 2 — EXTERNAL VC++ RUNTIME DEPENDENCY
The exact 0.0.32 GZFX.dll imports:
    MSVCP140.dll
    VCRUNTIME140.dll
    VCRUNTIME140_1.dll
    api-ms-win-crt-* runtime DLLs

This was introduced/retained by the /MD + x64-windows-static-md CommonLib build model.

A missing/incompatible Microsoft VC runtime causes Windows LoadLibrary to fail before:
    DllMain
    SKSEPlugin_Preload
    SKSEPlugin_Load
    any GZFX log/output

CI runners have the Visual Studio runtime installed, so the existing tests cannot detect a clean-machine dependency failure.

UNVALIDATED REAL-RUNTIME RISK 3 — COMMONLIB API INIT CONTRACT
0.0.32 linked CommonLibSSE-GG but did not call:
    SKSE::Init(const SKSE::LoadInterface*, ...)

The pinned CommonLib implementation's SKSE::Init explicitly initializes:
    REL::Module
    REL::IDDatabase
    CommonLib SKSE API storage/interfaces

GZFX manually touched REL::Module and later relocation-backed RE singletons, but bypassed the library's normal SKSE initialization contract.

This omission does not explain failure before LoadLibrary by itself, but it is an integration defect that must be corrected before the next field test.

CURRENT VERDICT
0.0.32 automated acceptance is not sufficient for the real SKSE front door.
Real field evidence overrides it.

The next bounded engineering wave must:
1. remove avoidable dynamic VC runtime dependencies;
2. make SKSEPlugin_Preload minimal and non-invasive;
3. arm GZFX D3D observation in normal SKSEPlugin_Load instead;
4. initialize CommonLib through its supported SKSE::Init contract;
5. retain exact-runtime fail-closed behavior and all locked renderer semantics;
6. add CI gates that inspect the produced DLL imports and exercise the revised phase contract.
