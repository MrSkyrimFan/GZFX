======================================================================
3. FALSE-POSITIVE HYPOTHESIS A
"ANY TINY RGBA16F CHAIN COULD LOOK LIKE HDR"
======================================================================

Rejected.

The 0.0.29 detector does not accept an arbitrary tiny chain.

Its root must read:

    canonical MAIN_HDR
    or
    one of a bounded set of verified full-resolution HDR descendants rooted in
    MAIN_HDR.

Continuation requires:

    read of prior chain output;
    non-increasing dimensions;
    strictly decreasing area.

Terminal requires:

    coherent chain step count;
    width <=2;
    height <=2.

Pre-field no-drift CI explicitly proves an unrelated full-resolution float16
branch followed by a complete downsample-to-2x2 chain is rejected:

    hdr_unrelated_fullres_rejected

PASS.

The real field result then independently replayed the same structural algorithm
against raw resource identities with zero frame mismatch.

Therefore:

    "arbitrary small chain" is not a viable explanation.

======================================================================
4. FALSE-POSITIVE HYPOTHESIS B
"THE 2x2 TERMINAL MAY BE REAL, BUT NOT EXPOSURE/ADAPTATION"
======================================================================

Strongly rejected.

Evidence is conjunctive:

1. the chain is MAIN_HDR-descended;

2. it is float16 throughout the reduction family;

3. it reaches a true <=2x2 terminal on every active scene frame;

4. the terminal is consumed immediately downstream by the stable
   full-resolution image-space transition;

5. current public ISHDR.hlsl has a DOWNSAMPLE family with:
       luminance variants;
       AdaptTex;
       DOWNADAPT behavior;

6. its BLEND family samples:
       AvgTex

   and uses:
       avgValue

   in exposure behavior before tonemapping.

This makes the exposure/adaptation interpretation substantially more specific
than simple size coincidence.

Pass 2 finds no plausible competing interpretation that explains all six facts.

======================================================================
5. FALSE-POSITIVE HYPOTHESIS C
"BEFORETONEMAP MAY BE MISNAMED OR MISORDERED"
======================================================================

Rejected, with one documentation nuance.

Current GZFX behavior signals BeforeTonemap:

    BEFORE execution

of the first full-resolution R8G8B8A8_UNORM pass that:

    follows completed HDRReduction;
    reads the final reduction/adaptation terminal identity.

Therefore the GZFX event is mechanically a pre-execution boundary.

Independent public Skyrim renderer evidence is unusually explicit.

Current Community Shaders State.h describes a per-frame:

    TonemapOwner

and documents:

    kVanilla:
        "Vanilla ISHDR tonemap runs unmodified."

It also describes HandlePostProcessing as dispatching:

    "the HDR tonemap pass"

with:
    input scene render target
    output tonemapped render target.

Current Hooks.cpp wraps a Skyrim path named:

    Main_HDRTonemapBlendCinematic_Render

and current PostProcessing.h explicitly says:

    "Tonemap-time entry is driven by
     PostProcessingExtensions::Main_HDRTonemapBlendCinematic_Render"

Current ISHDR.hlsl BLEND performs:

    adaptation/exposure;
    Reinhard or Hejl-Burgess-Dawson tonemapping;
    bloom;
    saturation;
    tint;
    contrast;
    cinematic intensity;
    fade.

Therefore the event name BeforeTonemap is semantically justified.

Nuance:

    the engine pass is compound.

Recommended definition:

    BeforeTonemap =
        immediately before Skyrim's HDR tonemap/blend/cinematic image-space
        pass.

Do not claim it is a boundary before every later color operation or display
mapping path that a future mod/framework might introduce.

======================================================================
7. FALSE-POSITIVE HYPOTHESIS E
"SHADER HASH CONFIRMATION COULD BE FOOLING US"
======================================================================

Rejected because shader hash is not the authority.

The 0.0.29 field session itself contains a useful counterexample:

    stable global TAA PS
        0xE8D58B595587B316

appears in two extra raw rows on:

    frame 10802
    frame 11903

yet semantic TAA remains exactly once per active frame.

Therefore the implementation does not simply map:

    hash -> semantic.

HDR/Tonemap authority is:

    resource identity
    shape
    same-frame lineage
    bounded source ancestry
    execution ordering
    terminal dependency.

Stable hashes are forensic corroboration only.

This makes the successful field result harder, not easier, to explain as a
hash collision/overfit artifact.

======================================================================
8. D3D11 API MODEL RECHECK
======================================================================

Microsoft's documented state model continues to support GZFX's interpretation.

PSSetShaderResources:

    binds explicit SRV interfaces.

OMSetRenderTargets:

    binds explicit RTV/DSV interfaces.

Both APIs enforce conflict behavior for overlapping resource subranges.

This means the resource bindings observed by GZFX are actual runtime D3D11
state, not names inferred from external metadata.

Current ReShade also exposes first-class events for:

    resource/view lifecycle;
    bind_render_targets_and_depth_stencil;
    bind pipeline/shaders;
    draw;
    dispatch;
    present;
    finish_present.

Its generic depth example tracks resource candidates across real rendering
events.

Pass-2 conclusion:

    structural D3D resource identity is an appropriate foundation for a
    runtime-independent GZFX semantic contract.

9. RUNTIME PORTABILITY FALSIFICATION
======================================================================

This is the strongest limitation found by Pass 2.

Current field certification is ONLY:

    SkyrimSE.exe 1.7.104.0

The structural detector itself is not dependent on executable offsets.

Therefore it is reasonable to lock:

    the architecture / structural semantic contract.

It is NOT reasonable to claim:

    real-field certification on every supported runtime family.

Current support language must distinguish:

ARCHITECTURE:
    runtime-independent D3D11 contract
    locked

FIELD CERTIFICATION:
    1.7.104:
        proven

    1.5.97:
        pending

    common 1.6.x families:
        pending except for unrelated engine-profile validation where already
        proven

    1.7.99:
        pending

    1.6.1179:
        pending

This is a scope constraint, not a reason to withhold promotion on the tested
runtime.

10. POSTTONEMAPPREUI ADVERSARIAL REVIEW
======================================================================

Pass 2 tried to determine whether HDR/Tonemap closure now makes
PostTonemapPreUi automatically obvious.

It does not.

Current public Community Shaders source provides an excellent semantic clue:

    MenuManagerDrawInterfaceStart

Current Hooks.cpp comment:

    "Disable scene TAA for the duration of the menu interface render"

Current Upscaling.cpp comment around the same hook:

    redirect framebuffer before vanilla UI renders.

This strongly confirms that the engine location is a real UI transition.

But the 0.0.29 GZFX field session does NOT have a verified 1.7.104 executable
PRE_UI engine epoch.

Historical Research Pass 9 explicitly required field correlation among:

    post-processing;
    global TAA;
    final full-resolution target;
    actual DXGI Present;
    pre-UI engine landmark

before renaming/promoting PostTonemapPreUi.

That condition is still unmet.

Therefore:

    PostTonemapPreUi remains unpromoted.

Do not equate:

    AfterGlobalTAA

with:

    PostTonemapPreUi.

There can still be legitimate scene/image-space work between TAA and UI.
