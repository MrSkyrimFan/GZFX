======================================================================
4. WHY THIS RESULT IS STRONGER THAN SIMPLY CHANGING ONE CONDITION
======================================================================

A trivial patch such as:

    allow ancestry when step != 0

is underspecified.

It does not define:

    whether the active reduction chain should reset;
    whether the previous source should be forgotten;
    how sibling branches coexist;
    how many candidates are legal;
    what ancestry depth remains legal.

The source-set model answers each question explicitly:

    full-res ancestry remains observable while HDR is incomplete;

    observing a new candidate does NOT destroy the current reduction chain;

    only a later incompatible downsample that reads a verified source causes
    normal fresh-root restart;

    old verified source branches remain available;

    candidate count and depth are bounded.

That is materially safer than a single boolean-condition change.

======================================================================
5. ALTERNATIVE REPAIR RE-EVALUATION
======================================================================

A. ALWAYS RESET THE CHAIN WHEN A NEW FULL-RES HDR DESCENDANT APPEARS

This would fix the field data.

Rejected after second review because:

    it may discard a valid reduction chain merely because another legitimate
    full-resolution post-processing branch exists.

The field data does not require destructive reset.


B. REPLACE SOURCE WITH THE LATEST FULL-RES DESCENDANT

Also fixes the observed field.

Rejected because:

    it preserves the original greedy single-source architecture.

It can simply fail in the opposite direction if multiple sibling branches are
valid.


C. KEEP A BOUNDED SOURCE SET; ONE REDUCTION CHAIN

Still preferred.

It adds only the missing memory of verified sibling sources while preserving
all current terminal/restart logic.


D. MULTIPLE FULL REDUCTION CHAINS IN PARALLEL

Not currently necessary.

The real field topology needs multiple source hypotheses but only one active
descending chain at a time.

Parallel reduction-chain state would add complexity without evidence.

Do not build it until contradictory field evidence requires it.

======================================================================
7. CAPACITY REVIEW
======================================================================

Real field requirement:

    maximum derived source candidates per active frame:
        1

Pass-1 proposal:

    fixed capacity:
        4

Pass-2 verdict:

    4 is conservative and acceptable.

It is not justified to make this dynamic/unbounded.

Capacity-full behavior must be:

    do not evict an older verified source merely to admit a new one;
    fail closed on the additional source.

Why no eviction:

    eviction would introduce a new heuristic choice about which branch matters.

A fixed set preserves deterministic behavior.

======================================================================
9. ROOT ELIGIBILITY SHOULD BE IDENTITY-STRUCTURAL
======================================================================

Root admission must ask:

    does this downsample read canonical MAIN_HDR
    OR one of the bounded verified full-res HDR source identities?

It must NOT ask:

    is pixel shader hash F026...?
    is this draw exactly 27 ordinals after some earlier draw?
    is this resource pointer 0x251E...?
    are we in an interior?

Those field values prove the defect.

They are not the contract.

This distinction is critical for runtime portability.

======================================================================
10. D3D11 REFERENCE RECHECK
======================================================================

Microsoft's D3D11 binding semantics again support exact resource lineage:

    PSSetShaderResources binds concrete resource views for reading;

    OMSetRenderTargets binds concrete output views;

    overlapping read/write subresources are nulled rather than silently
    remaining simultaneously bound.

Therefore using the observed read/write resource identities as graph edges is
sound for this bounded purpose.

No additional engine hook is required to know that a full-resolution HDR output
was derived from MAIN_HDR.

======================================================================
11. RESHADE / RENDERDOC / 3DMIGOTO CROSS-CHECK
======================================================================

Second-pass architecture comparison:

ReShade generic depth tracking:
    keeps a per-frame collection of candidate depth resources and accumulated
    evidence instead of treating the first plausible resource as final.

ReShade API:
    exposes resource/view lifecycle and render-target/shader-resource binding
    as first-class events.

RenderDoc D3D11 replay:
    maintains ResourceId-based resource descriptions and event usage rather
    than reducing renderer identity to shader hashes.

3Dmigoto:
    tracks render targets/resources and explicitly documents limitations and
    contamination concerns around hash-only identity.

Independent lesson:

    bounded identity/state tracking is the mature pattern;
    first-match shader/hash inference is not.

The GZFX proposal follows that architectural direction while remaining
independently implemented.

======================================================================
12. SKYRIM COMMUNITY SHADERS CROSS-CHECK
======================================================================

Current Community Shaders HDR Display source explicitly intercepts Skyrim's
ImageSpaceManager post-processing path and manipulates float16 HDR targets.

This again supports the possibility of multiple same-frame full-resolution HDR
branches inside Skyrim post-processing.

The correct GZFX detector therefore needs branch tolerance.

It should not assume the first MAIN_HDR-descended image-space branch is the only
one.
