======================================================================
1. EXECUTIVE CONCLUSION
======================================================================

Yes: inspecting ReShade side-by-side with ENB was useful and materially changes
the next architecture recommendation.

The two frameworks solve different halves of the problem exceptionally well.

ENB demonstrates:

    deep Skyrim-specific renderer semantics;
    graphics-front-door ownership;
    persistent wrapped D3D objects;
    explicit pre/post display lifecycle;
    a multi-stage HDR / adaptation / post / water effect architecture;
    shader-specific Skyrim knowledge.

ReShade demonstrates:

    generic D3D11/DXGI lifecycle correctness;
    persistent wrapper identity;
    complete deferred-context / command-list lifecycle;
    explicit present AND finish-present events;
    resource/pipeline creation lifecycle;
    robust third-party-hook coexistence machinery;
    delayed module-hook installation;
    API-agnostic effect/runtime boundaries.

The key shared architecture is:

    graphics API front door
    ->
    persistent identity
    ->
    explicit object lifecycle
    ->
    explicit frame/present lifecycle
    ->
    game-specific semantics layered on top.

GZFX 0.0.26 now proves that its current D3D observation architecture can
provide stable identities and strong semantic reconstruction.

However, the field DATA exposes one remaining architectural weakness:

    GZFX.dll itself is not guaranteed to initialize at the graphics front door.

The current dinput8 bootstrap DLL is loaded early, but it lazy-loads GZFX.dll
only from Prepare(), which is called when Skyrim invokes one of the exported
DirectInput functions.

Therefore some long-lived core renderer resources can exist before GZFX's D3D
creation hooks arm.

This is consistent with 0.0.26 field evidence:

    23,230 resources were observed at creation;
    16,126 shaders were observed at creation;
    late Skyrim image-space shaders have strong SkyrimSE.exe provenance;
    yet important long-lived core semantic targets remain
        unknown/preexisting.

This does NOT justify moving heavy GZFX initialization into DllMain.

Microsoft explicitly warns that DllMain runs under the loader lock and that
LoadLibrary/LoadLibraryEx must not be called from there.

The strongest next architecture is therefore a SAFE graphics-front-door
bootstrap, not a loader-lock hack.

Research recommendation for the next BLUEPRINT:

    1. preserve the proven GZFX renderer core;
    2. add a minimal graphics-front-door bootstrap mechanism that invokes
       GZFX initialization from a real D3D11/DXGI API call, outside DllMain;
    3. retain dinput8 for input/bootstrap compatibility where useful;
    4. design explicit proxy chaining/coexistence rather than assuming GZFX is
       the only graphics proxy;
    5. add a verified Skyrim 1.7.104 engine profile;
    6. repair the two now-proven HDR detector defects;
    7. lock global TAA only after blueprint acceptance rules are written;
    8. keep ENB and ReShade as architectural references, not code donors.

This is no longer broad renderer discovery.

It is renderer-entry, version-profile, and semantic-contract hardening.

======================================================================
4. RESHADE PERSISTENT D3D11 WRAPPER MODEL
======================================================================

ReShade's public D3D11 implementation wraps persistent interfaces.

Examples:

    D3D11Device
    D3D11DeviceContext
    D3D11CommandList
    DXGISwapChain

CreateDeferredContext:

    calls the original device;
    obtains the real deferred context;
    creates a ReShade D3D11DeviceContext proxy;
    returns the proxy to the application.

The application therefore continues calling through ReShade for the entire
lifetime of that context.

CreateVertexShader / CreatePixelShader / other shader creation:

    receive the real shader bytecode;
    expose a pipeline/shader description to the add-on layer;
    call original creation;
    emit pipeline initialization lifecycle events.

The architecture maintains identity from birth rather than discovering it only
when an object later appears bound.

This independently validates GZFX 0.0.26's creation-time identity direction.

======================================================================
5. RESHADE COMMAND-LIST LIFECYCLE
======================================================================

ReShade's D3D11 deferred-command lifecycle is explicit.

FinishCommandList:

    emits close_command_list;
    calls the original FinishCommandList;
    wraps the returned ID3D11CommandList;
    associates the returned command list with the recording context;
    emits execute_secondary_command_list relationship evidence;
    emits reset_command_list when RestoreDeferredContextState is false.

ExecuteCommandList:

    receives the wrapped list;
    emits execute_secondary_command_list;
    unwraps to the original D3D11 command list;
    executes the original list;
    emits default-state behavior when RestoreContextState is false.

Immediate-context Flush:

    emits execute_command_list for the immediate command list.

Research lesson:

    command-list identity is a lifecycle contract, not a pointer classification.

GZFX 0.0.26 reached the same conceptual model independently and the field
session confirmed its ownership repair:

    26,370 / 26,370 lists = GZFX-owned
    external = 0.

Therefore ReShade supports preserving the current GZFX command-list architecture
rather than replacing it.

9. GZFX CURRENT BOOTSTRAP — IMPORTANT TIMING FACT
======================================================================

Current package:

    SkyrimSE.exe
    -> local dinput8.dll
    -> GZFX.dll

But source review shows an important timing distinction.

bootstrap/dinput8_proxy.cpp:

DllMain on DLL_PROCESS_ATTACH only:

    stores g_proxyModule;
    calls DisableThreadLibraryCalls.

It does NOT:

    LoadLibrary(GZFX.dll);
    initialize GZFX;
    arm D3D hooks.

GZFX is lazy-loaded through:

    exported dinput8 function
    ->
    Prepare()
    ->
    EnsureRealDInput()
    ->
    EnsureGzfx()
    ->
    LoadGzfx()
    ->
    LoadLibraryW(GZFX.dll)
    ->
    GZFX_Initialize()

Therefore the actual renderer instrumentation start time is:

    first use of a dinput8 exported function

not:

    dinput8 proxy DLL load time.

This is a meaningful difference from ENB/ReShade.

They are activated by the graphics API entry path itself.

11. DO NOT MOVE HEAVY INITIALIZATION INTO DLLMAIN
======================================================================

A naive response would be:

    "just LoadLibrary GZFX.dll from dinput8 DllMain."

Do NOT do that.

Microsoft's DLL guidance states:

    DllMain executes while the process loader lock is held.

Microsoft explicitly warns against:

    LoadLibrary
    LoadLibraryEx

inside DllMain because it can deadlock or crash.

It recommends minimizing DllMain and deferring significant initialization.

Therefore:

    current minimal dinput8 DllMain is good loader-lock discipline.

The next architecture must obtain earlier graphics timing WITHOUT doing unsafe
heavy work under loader lock.

Microsoft references:

    https://learn.microsoft.com/windows/win32/Dlls/dynamic-link-library-best-practices
    https://learn.microsoft.com/windows/win32/Dlls/dllmain

12. SAFE GRAPHICS-FRONT-DOOR OPTIONS
======================================================================

Research ranks the options as follows.

----------------------------------------------------------------------
OPTION A — MINIMAL D3D11 FRONT-DOOR PROXY / BOOTSTRAP

Shape:

    SkyrimSE.exe
    -> GZFX d3d11.dll bootstrap
    -> first exported D3D11 API call
    -> initialize GZFX OUTSIDE DllMain
    -> forward to real/chained D3D11

Advantages:

    earliest deterministic renderer entry;
    captures device/resources/shaders from birth;
    same proven architectural class as ENB/ReShade;
    cleanly outside loader-lock once the exported D3D call is invoked;
    directly solves preexisting core-resource problem.

Risks:

    filename collision with ENB/ReShade;
    proxy chaining complexity;
    additional package/bootstrap component;
    COM/API forwarding correctness must be extremely robust.

Mitigation:

    implement explicit chain support;
    keep the bootstrap tiny;
    forward all exports faithfully;
    test with system D3D11 and known proxy-chain arrangements;
    do not move renderer logic into the shim.

Research rank:

    STRONGEST ARCHITECTURAL OPTION

----------------------------------------------------------------------
OPTION B — EARLIER DINPUT8-BASED THUNK / IMPORT PATCH

Concept:

    keep dinput8 as the only proxy;
    install only a tiny early D3D interception thunk before GZFX.dll loads;
    thunk lazily initializes GZFX on first graphics API call.

Potential advantage:

    avoids claiming d3d11.dll filename.

Problems:

    to beat resource creation, the patch itself must be installed before the
    first D3D call;
    doing PE/IAT patching from DllMain increases loader-lock complexity;
    implementation becomes a custom miniature loader/hook system inside the
    bootstrap;
    harder to reason about than a graphics proxy.

Research rank:

    POSSIBLE BUT NOT PREFERRED WITHOUT STRONGER NEED

----------------------------------------------------------------------
OPTION C — KEEP CURRENT LAZY DINPUT BOOTSTRAP

Advantages:

    already proven;
    least disruptive;
    compatible with graphics proxies.

Disadvantage:

    cannot guarantee observation of core renderer-object birth.

This may be acceptable if GZFX can identify all required core resources later,
but the project's long-term goal is complete renderer ownership.

Research rank:

    SAFE FALLBACK
    PROBABLY INSUFFICIENT AS FINAL ARCHITECTURE

----------------------------------------------------------------------
OPTION D — HEAVY DLLMAIN INITIALIZATION

Research rank:

    REJECTED

Reason:

    loader-lock risk;
    Microsoft explicitly warns against LoadLibrary from DllMain.

13. PROXY-CHAIN DESIGN IS NOT OPTIONAL IF OPTION A IS CHOSEN
======================================================================

GZFX's long-term product intends to replace ENB/ReShade graphics roles.

During development and for user compatibility, graphics-proxy coexistence still
matters.

Both ENB and ReShade expose proxy/chaining concepts.

A GZFX graphics bootstrap should therefore be designed to:

    load the real system d3d11.dll by absolute system path when no chain exists;

    optionally load a configured chained proxy library;

    never recursively load itself;

    expose/forward the full expected D3D11 export surface;

    record which downstream module actually supplies each D3D11 export;

    detect known/unknown proxy layers;

    fail closed rather than overwrite another local d3d11.dll silently.

Possible package model:

    dinput8.dll
        retains GZFX input interception

    optional/new d3d11.dll
        renderer bootstrap only

    GZFX.dll
        all actual renderer logic

    configurable chain filename
        e.g. d3d11_gzfx_chain.dll

The exact filename/config is a BLUEPRINT decision, not established here.
