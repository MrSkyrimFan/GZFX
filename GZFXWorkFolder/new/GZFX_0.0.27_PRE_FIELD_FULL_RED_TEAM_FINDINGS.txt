7. RED-TEAM FINDING A — STARTUP TRACE CAN MIX MULTIPLE RUNS
======================================================================

Current source:

    src/diagnostics/startup_trace.cpp

writes:

    Diagnostics/renderer_startup.csv

in append mode.

The file is shared across launches.

Current behavior does not create a process/session boundary in the file and does
not truncate it on the first Record() of a fresh process.

Therefore a later field upload can contain:

    launch N startup rows
    launch N+1 startup rows
    launch N+2 startup rows

in one file.

This can make startup ordering appear valid or invalid based on stale evidence
from another process.

DATA classification:

    REAL FORENSIC INTEGRITY DEFECT

Required next-wave direction:

    first startup Record() in each process must create/truncate;
    subsequent calls append;
    include PID and a monotonic sequence.

8. RED-TEAM FINDING B — FIRST SUCCESSFUL D3D DEVICE CAN POISON PRIMARY
======================================================================

Current d3d11 front-door behavior attempts to attach the first successful D3D11
device/context returned through the proxy.

This is too broad.

Potential pre-Skyrim devices include:

    WARP;
    REFERENCE;
    SOFTWARE;
    Microsoft Basic Render Driver;
    diagnostic/helper devices.

If such a device is attached first, current primary-object code rejects a
different device later.

Therefore the real Skyrim hardware renderer could be rejected after a helper
device wins the race.

Public mature D3D11 frameworks explicitly distinguish software/reference/basic
devices from real application hardware renderers.

DATA classification:

    REAL PRIMARY-SELECTION RISK

Required direction:

    qualify primary candidates before attaching.

Real process criteria should include:

    hardware-class device;
    not WARP;
    not REFERENCE;
    not SOFTWARE;
    not NULL;
    not Microsoft Basic Render Driver;
    main-executable caller provenance where available;
    process-owned output window when a swapchain is supplied.

Tests may explicitly opt WARP in.

9. RED-TEAM FINDING C — D3D-FIRST AND GZFX-FIRST PATHS ARE NOT EQUIVALENT
======================================================================

0.0.27 correctly added explicit pre-Present renderer attach from the d3d11
front door.

But another supported startup order remains:

    dinput8 path loads GZFX first
    ->
    GZFX ArmD3D11LifecycleProbe patches Skyrim's D3D IAT
    ->
    Skyrim later calls D3D11CreateDevice[AndSwapChain].

In that path:

    d3d11_lifecycle currently attaches pipeline_cartography
    and renderer_execution_service,

but it does NOT call:

    renderer_forensics::AttachPrimaryRendererObjects.

Result:

    creation hooks can still capture resource/shader birth,
    but immediate-context renderer-forensics observation may wait until first
    Present.

That means pre-Present context commands can differ between startup orders.

DATA classification:

    REAL STARTUP-PARITY DEFECT

Required direction:

    d3d11_lifecycle successful primary creation path must explicitly attach the
    renderer-forensics primary objects too.

Add an acceptance test for GZFX-first pre-Present attachment.

10. RED-TEAM FINDING D — D3D11 PROXY EXPORT CONTRACT IS MISALIGNED
======================================================================

0.0.27 d3d11.dll exports:

    D3D11CreateDevice
    D3D11CreateDeviceAndSwapChain

plus undocumented/internal:

    D3D11CoreCreateDevice
    D3D11CoreCreateLayeredDevice
    D3D11CoreGetLayeredDeviceSize
    D3D11CoreRegisterLayers

but does NOT export:

    D3D11On12CreateDevice

which is a documented D3D11 API entry point.

The partial D3D11Core export set also does not reproduce the full historic
internal d3d11.dll ordinal surface.

Because GZFX's proxy is a product bootstrap, it should make the narrowest
truthful public API promise rather than pretending a partial undocumented ABI is
stable.

DATA classification:

    REAL PROXY-CONTRACT DEFECT

Required next-wave direction:

    export/forward documented public D3D11 entry points:
        D3D11CreateDevice
        D3D11CreateDeviceAndSwapChain
        D3D11On12CreateDevice

    remove partial D3D11Core wrappers from the GZFX public proxy contract.

D3D11On12CreateDevice should forward only and must not claim Skyrim-primary
ownership.

11. RED-TEAM FINDING E — REAL SKYRIM CLEAN SHUTDOWN IS NOT PROVEN BY TESTS
======================================================================

Important source correction:

    runtime.cpp DOES register std::atexit when telemetry initializes in a
    non-test process.

However:

    all relevant harnesses call GZFX_Shutdown manually.

Therefore the automated clean-shutdown proof does NOT exercise Skyrim's real
automatic-exit path.

Real 0.0.25 and 0.0.26 field uploads repeatedly lacked:

    telemetry_session_complete.txt

despite drained queues.

That means the current automatic shutdown path is not producing the desired
field closure evidence.

The current telemetry Shutdown performs:

    file writes;
    ring drain;
    writer-thread wake;
    writer-thread join;
    final file flush.

That work should happen before process teardown begins, while worker threads are
still alive, not during late DLL/CRT teardown.

DATA classification:

    PROVEN FIELD CLOSURE DEFECT
    CURRENT AUTOMATED TEST IS INSUFFICIENT

Required direction:

    remove dependency on DLL std::atexit for process-level telemetry closure.

Preferred next-wave mechanism:

    intercept ExitProcess before the real ExitProcess call;
    call GZFX_Shutdown exactly once;
    allow telemetry to drain/join/flush;
    then call the original ExitProcess.

The process-exit hook should live in the long-lived d3d11 bootstrap rather than
inside unloadable GZFX.dll.

Add a parent/child test where the child exits normally WITHOUT calling
GZFX_Shutdown manually.
