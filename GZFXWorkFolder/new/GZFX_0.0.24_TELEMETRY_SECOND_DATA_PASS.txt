9. EXPLICIT COPY / RESOLVE / CLEAR LINEAGE — CORRECTION
======================================================================

The first DATA report said compact continuous telemetry did not preserve
explicit copy/resolve/clear operands and therefore some operations appeared
without producer information.

That conclusion is directionally correct but the exact failure mode is more
subtle.

Observed compact rows for operations such as:

    CopyResource
    ClearRTV
    ClearDSV
    ExecuteCommandList

often contain NONZERO read/write IDs.

However these IDs are NOT the explicit operation operands.

They are inherited from the currently tracked bound pipeline state because
PassTelemetry is built from g_state before/around the explicit operation.

Concrete evidence:

frame 1914 ordinal 5527:
    Draw row
    followed by CopyResource row

Both carry the same R16 output/read binding set.

frame 9386 ordinal 3637:
    same pattern.

Therefore the correct statement is:

    explicit-operation lineage is not absent;
    it is contaminated by stale/current bound-state lineage and cannot be
    trusted as the operation's true source/destination/view operands.

This applies especially to:

    CopyResource
    CopySubresourceRegion
    ResolveSubresource
    ClearRTV
    ClearDSV
    ClearUAV
    ExecuteCommandList

Future telemetry must carry those operations' explicit operands directly.

======================================================================

PassTelemetry stores only:

    up to 8 unique concrete read resource identities

and:

    up to 8 unique concrete write identities.

The full read/write hashes still describe the complete bound-state set, but
the concrete identity list is bounded.

Late-stack review:

read_count distribution:

        503,194
        71.69%

Because read_count itself saturates at the storage capacity, a value of 8
means:

    8 OR MORE

not necessarily exactly 8.

Therefore:

    at least 71.69% of late-stack rows do not prove that their concrete read
    list is exhaustive.

Breakdown of read_count=8:

EXTERIOR:
    312,355 rows

    190,839 rows

Main kinds at the cap:

    454,160

    39,246

    7,099

This is a major lineage limitation missed in the first report.

The full binding hashes remain useful for equality/change detection.

But exact producer->consumer reconstruction requires a better identity
transport for high-fan-in passes.
