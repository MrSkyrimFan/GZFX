GZFX 0.0.33 SKSE LOADER RESCUE — TARGETED RESEARCH
Date: 2026-11-05

QUESTION 1
Can SKSEPlugin_Preload safely be reduced without abandoning the SKSE architecture?

ANSWER
Yes.

Official SKSE 2.3.1 source:
    ianpatt/skse64
    current source commit inspected: 25b72352adb6543fa6d0bd3795780672b2e238e0

PluginManager installs plugins in two phases:
    kPhase_Preload
    kPhase_Load

SKSEPlugin_Preload is optional and upstream documentation states that game and SKSE functionality is limited during preload.

Normal SKSEPlugin_Load remains before normal game execution proceeds after SKSE's startup integration. GZFX can therefore retain the official SKSE front door while removing invasive PE/IAT mutation from the constrained preload phase.

RESEARCH DECISION
Keep SKSEPlugin_Preload only as compatibility acceptance / phase evidence.
Move ArmEarlyGraphicsBootstrap to SKSEPlugin_Load before GZFX_Initialize.
GZFX_Initialize already arms renderer-forensics and calls the same D3D lifecycle probe through call_once, so this remains a single coherent arm path.

QUESTION 2
Should GZFX remain dependent on the separately installed Microsoft VC++ runtime?

ANSWER
No practical need exists for the field-test/product DLL.

Current 0.0.32 uses:
    vcpkg triplet x64-windows-static-md
    MSVC /MD dynamic CRT

The exact shipped DLL imports MSVCP140/VCRUNTIME140/VCRUNTIME140_1.

The pinned CommonLib source supports source builds when a non-DLL MSVC runtime is selected. Its prebuilt optimization explicitly falls back to source when CMAKE_MSVC_RUNTIME_LIBRARY is not a DLL runtime.

RESEARCH DECISION
Use:
    VCPKG_TARGET_TRIPLET=x64-windows-static
    CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded$<$<CONFIG:Debug>:Debug>

This keeps vcpkg dependencies and the MSVC runtime statically linked where supported and removes an avoidable clean-machine LoadLibrary dependency class.

System Windows/D3D DLLs remain normal OS dependencies.

QUESTION 3
Should GZFX call CommonLib's normal SKSE initializer?

ANSWER
Yes.

Pinned dependency:
    eddoursul/CommonLibSSE-GG
    2053e94fd1c147b36eae2b4338118552fba407e2

Its API declares:
    SKSE::Init(const SKSE::LoadInterface*, bool)

Implementation initializes:
    REL::Module::get()
    REL::IDDatabase::get()
    CommonLib SKSE API storage
    queried SKSE interfaces

CommonLib LoadInterface is a zero-data wrapper over the raw SKSE interface pointer; its GetProxy() reinterprets this as detail::SKSEInterface.

GZFX's custom gzfx::skse::Interface was already verified layout-compatible with official SKSE 2.3.1.

RESEARCH DECISION
Add a bounded commonlib bridge function that receives the raw GZFX SKSE interface pointer and, only after:
    exact runtime validation
    Address Library file presence
calls:
    SKSE::Init(reinterpret_cast<const SKSE::LoadInterface*>(raw), false)

The existing CI test override must bypass real REL/Address Library initialization in non-Skyrim harness processes.

QUESTION 4
Can the field failure be declared fully root-caused without the user's SKSE log?

ANSWER
No.

The observed topology proves failure before healthy GZFX runtime output.
It does not distinguish with certainty among:
    Windows LoadLibrary dependency failure
    Preload-phase exception/rejection
    another early loader failure

The engineering response should therefore remove all three known integration defects/risks above in one bounded rescue wave and improve proof, rather than guessing one cause.

END RESEARCH
