======================================================================
3. HIGH-LEVEL ARCHITECTURE
======================================================================

Renderer thread:

    existing D3D11 hooks / Stage Scheduler / Semantic Authority /
    Pipeline Cartography
    ->
    copy compact fixed-size numeric records
    ->
    bounded lock-free event ring

Dedicated writer thread:

    drain ring
    ->
    format CSV/TXT
    ->
    write session files
    ->
    rotate large pipeline files
    ->
    update health/status

The writer thread does NOT:

    call the D3D11 immediate context
    call DXGI Present
    query renderer state
    Map GPU resources
    resolve GPU timestamp queries
    call Skyrim rendering functions.

This preserves the D3D11 immediate-context threading boundary.

======================================================================
6. EVENT RING
======================================================================

The listener uses a preallocated bounded lock-free ring based on per-slot
sequence ownership.

Producer behavior:

    reserve slot atomically
    copy POD event
    publish sequence

Consumer:

    writer thread drains independently.

If ring is full:

    event is dropped
    dropped counter increments
    producer returns immediately.

The renderer thread never waits for writer progress.

======================================================================
7. RING CAPACITY ENGINEERING DEVIATION
======================================================================

The research/blueprint proposed:

    262,144 records.

Final default:

    65,536 records.

Reason:

During implementation, the event payload was deliberately expanded to retain
concrete producer/consumer resource identities, not merely hashes.

A 65,536-record default bounds forensic memory while still providing a large
burst buffer.

The exact runtime:

    ring_capacity
    event_bytes
    queue_high_water
    dropped

are written into the session manifest/status.

The capacity can be revisited from real listener evidence.

This is preferable to allocating a much larger ring before observing actual
Skyrim queue pressure.

8. DETERMINISTIC OVERFLOW BEHAVIOR
======================================================================

Telemetry MUST fail soft.

A dedicated CI test reduces the ring to:

    64 records

and deliberately fills it before the writer starts.

Expected:

    producer does not block
    process continues
    dropped > 0
    listener status becomes degraded
    session still completes.

This test passes.

The normal telemetry listener test separately requires:

    dropped = 0.

This proves both:

    normal healthy operation
    and
    bounded failure behavior.

======================================================================
10. PASS-FAMILY COMPRESSION
======================================================================

A raw Skyrim frame can contain many repeated geometry draws.

Logging each one as a full text row would be unnecessarily expensive.

The listener creates a compact pass-family signature from:

    pass kind
    draw kind
    shader identities/hashes
    RTV identities
    DSV identity
    OM/CS UAV hashes
    read-resource hash
    write-resource hash
    constant-buffer hash
    sampler hash
    blend state
    depth state
    raster state
    topology
    viewport

Adjacent same-family passes in the same frame are compressed into:

    first ordinal
    last ordinal
    repeat count
    representative args.

This preserves order and structural identity while reducing log volume.

======================================================================
11. PREEXISTING SKYRIM SHADERS
======================================================================

Safe field mode does not require experimental D3D device creation hooks.

Therefore some Skyrim shaders were created before GZFX observed bytecode
creation and have no bytecode fingerprint.

Pass telemetry uses:

    observed shader bytecode hash when available

otherwise:

    stable in-session shader object identity.

This prevents preexisting Skyrim passes from collapsing into an unhelpful
"shader 0" signature.

======================================================================
12. CONCRETE RESOURCE LINEAGE
======================================================================

Initial listener design retained:

    read-resource hash
    write-resource hash.

Before merge this was strengthened.

Each compact pass also preserves bounded concrete lists:

    up to 8 unique read resource identities
    up to 8 unique write resource identities

plus:

    read/write hashes for the full binding set.

This is important.

The next DATA pass can build actual:

    producer
    ->
    resource
    ->
    consumer

relationships instead of merely knowing that two pass binding sets differ.

The bounded lists cover the principal pass resources while the hashes still
detect changes outside the retained concrete list.

======================================================================
14. RESOURCE CALLBACK LOCK DEVIATION
======================================================================

The blueprint preferred calling all sinks after Pipeline Cartography releases
its internal mutex.

Pass telemetry follows that principle.

Resource first-discovery telemetry currently performs the listener callback
while the Pipeline Cartography mutex is held.

This is accepted for 0.0.24 because the callback:

    performs only a lock-free fixed-record enqueue
    does not call back into Pipeline Cartography
    does not format strings
    does not perform disk I/O
    does not perform D3D work.

There is no reentrant dependency.

If field telemetry identifies this as measurable contention, resource event
publication can be deferred outside the lock in a later repair.

21. TRANSITIONS
======================================================================

transitions.csv records high-value lifecycle changes:

    listener start/stop
    mode change
    environment change
    resolution change
    device generation change
    surface generation change
    Wave3 history generation change
    Wave4 history restart
    frame gap
    ResizeBuffers.

Queue saturation is also visible in listener health counters.

The beginning of an overflow episode may not itself fit in the ring when the

monotonic dropped counter/status.

======================================================================
23. TIMING TELEMETRY
======================================================================

The listener does NOT add GPU timestamp queries.

Wave3 and Wave4 continue using their existing asynchronous timing systems.

The listener records newer already-resolved CPU timing snapshots.

The writer thread never calls:

    ID3D11DeviceContext::GetData
    Flush
    Map.

This prevents the listener from becoming a GPU synchronization device.

======================================================================
24. WRITER THREAD
======================================================================

One dedicated writer thread:

    waits up to ~250 ms
    drains events in batches
    formats CSV/TXT
    flushes stream buffers roughly once per second
    updates listener_status.txt.

It performs no rendering calls.

No per-event FlushFileBuffers exists.

Pipeline files rotate at:

    64 MiB per segment.

26. TEST-HARNESS LIFECYCLE
======================================================================

Legacy GZFX harnesses dynamically unload GZFX.dll with FreeLibrary.

Leaving a listener writer thread or process-exit callback pointing inside an
unloaded DLL would be unsafe.

Therefore:

If:

    GZFX_TEST_OUTPUT_ROOT is active

and:

    GZFX_TEST_TELEMETRY_ACTIVE is not active

then:

    telemetry listener remains dormant.

The dedicated telemetry harness explicitly enables it and calls exported:

    GZFX_Shutdown()

before unloading the DLL.

The real Skyrim runtime registers best-effort normal-process shutdown through
atexit because GZFX remains loaded for the game process lifetime.

No blocking writer join is performed from DllMain/loader lock.

======================================================================
34. PERFORMANCE INTERPRETATION
======================================================================

0.0.24 is a FORENSIC build.

Do not use its FPS as release GZFX performance.

The listener is engineered to avoid the worst self-inflicted overhead:

    no new render-thread file writes
    no writer-thread D3D calls
    no render-thread queue blocking
    no listener GPU readback
    no forced GPU flush.

But it still:

    continuously tracks renderer state
    hashes pass state
    queues telemetry
    writes substantial session data.

Release performance must later be measured in a quiet build with forensic
telemetry disabled.
