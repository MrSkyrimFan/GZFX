======================================================================
2. MICROSOFT DIRECTINPUT CONTRACT
======================================================================

Microsoft DirectInput documentation confirms the same architecture used by the
historical GZFX implementation.

Reference:
    IDirectInput8::CreateDevice Method
    https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417803(v=vs.85)

Key contract:
    IDirectInput8::CreateDevice creates a device interface for a supplied GUID.
    GUID_SysMouse identifies the default system mouse.

Reference:
    IDirectInputDevice8::GetDeviceState Method
    https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417897(v=vs.85)

Key contract:
    GetDeviceState returns immediate device state.
    c_dfDIMouse maps to DIMOUSESTATE.
    c_dfDIMouse2 maps to DIMOUSESTATE2.
    Mouse relative axes are available as lX / lY / lZ.

Reference:
    DIDEVICEOBJECTDATA Structure
    https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416611(v=vs.85)

Key contract:
    buffered DirectInput events report object offsets and data.
    relative axis motion is represented in dwData.
    button state uses the high bit of the low byte.

Reference:
    Using DirectInput
    https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416845(v=vs.85)

Key contract:
    DirectInput8Create obtains the IDirectInput8 object.
    GUID_SysMouse may be passed to CreateDevice for the standard system mouse.

The historical GZFX hook chain is therefore aligned with the documented API.

======================================================================
3. WHY WIN32-ONLY INPUT IS NOT ENOUGH
======================================================================

Microsoft documents WM_INPUT / WM_MOUSEMOVE as valid mouse-input mechanisms,
but that does not imply they suppress another consumer's DirectInput stream.

Current GZFX WindowProc handles:
    WM_MOUSEMOVE
    WM_LBUTTONDOWN / UP
    WM_INPUT

The real field session proves this does not establish exclusive ownership of the
mouse for the overlay:
    Skyrim camera still moves.
    GZFX DirectInput packet count remains zero.

The correct repair must intercept the stream Skyrim itself consumes.

======================================================================
4. ARCHITECTURE OPTIONS
======================================================================

OPTION A — restore root dinput8.dll proxy
    REJECTED.

Reason:
    violates the owner-approved one-DLL SKSE architecture;
    reintroduces the retired distribution/AV-sensitive proxy design;
    package would no longer be exactly Data/SKSE/Plugins/GZFX.dll.

OPTION B — rely only on WindowProc raw/legacy mouse messages
    REJECTED.

Reason:
    already field-failed to own the mouse;
    does not stop Skyrim's DirectInput camera stream.

OPTION C — use CommonLib input events only
    NOT SELECTED FOR THIS REPAIR.

Reason:
    CommonLib gives useful typed engine access, but an event sink does not by
    itself guarantee that the same mouse motion cannot also reach Skyrim's look
    controls. The current defect is source ownership/suppression, not lack of an
    engine event observer.

OPTION D — migrate the proven DirectInput interception into GZFX.dll
    SELECTED.

This preserves:
    official SKSE loading;
    one GZFX DLL;
    system dinput8.dll;
    existing menu receiver;
    proven DirectInput semantics.

======================================================================
5. SELECTED INTERNAL ONE-DLL DIRECTINPUT CHAIN
======================================================================

Arm during normal SKSEPlugin_Load, never Preload.

Runtime chain:

    GZFX.dll
      -> load/locate system dinput8.dll
      -> MinHook dinput8!DirectInput8Create
      -> call original DirectInput8Create
      -> hook returned IDirectInput8::CreateDevice
      -> when GUID_SysMouse is created:
           remember the system mouse interface pointer
           hook IDirectInputDevice8::GetDeviceState
           hook IDirectInputDevice8::GetDeviceData
      -> menu closed:
           exact passthrough
      -> menu open:
           parse mouse deltas/buttons
           call gzfx::ui::SubmitDirectInputMouse
           suppress the same mouse data from Skyrim

No new proxy DLL is required.

======================================================================
6. SAFETY / SCOPE RULES
======================================================================

The runtime hook must be mouse-specific.

Unlike the historical proxy implementation, the new hook should not blindly
zero arbitrary GetDeviceState buffers merely because the hooked function target
might be shared.

Required guards:
    remember the actual GUID_SysMouse device interface pointer;
    only alter reads whose self pointer matches the recorded mouse device;
    accept immediate mouse state only for exact known mouse structure sizes:
        sizeof(DIMOUSESTATE)
        sizeof(DIMOUSESTATE2)
    leave every non-mouse device and unknown buffer untouched.

For GetDeviceData:
    only alter data for the recorded system mouse device;
    preserve DIGDD_PEEK behavior;
    only suppress consumed non-peek data while the menu is open;
    preserve original HRESULT.

When the menu is closed:
    no data mutation;
    no input suppression.

9. SKSE 2.3.1 DIRECTINPUT WRAPPER COMPATIBILITY
======================================================================

Official SKSE 2.3.1 source was inspected at:

    ianpatt/skse64
    25b72352adb6543fa6d0bd3795780672b2e238e0

SKSE initialization order in skse64.cpp is:

    g_pluginManager.InstallPlugins(kPhase_Load)
    g_pluginManager.LoadComplete()
    ...
    Hooks_DirectInput_Commit()

Therefore GZFX SKSEPlugin_Load executes before SKSE commits its DirectInput IAT
wrapper.

SKSE Hooks_DirectInput_Commit then:

    reads SkyrimSE.exe's existing dinput8!DirectInput8Create IAT target
    stores that address as DICreate_RealFunc
    replaces Skyrim's IAT slot with SKSE Hook_DirectInput8Create_Execute

SKSE's wrapper later calls:

    DICreate_RealFunc(...)

and its FakeDirectInput / FakeDirectInputDevice wrappers ultimately call the
real IDirectInput8 and real IDirectInputDevice8 methods.

This is compatible with the selected 0.0.34 design:

1. During GZFX SKSEPlugin_Load, MinHook patches the real
   dinput8!DirectInput8Create function entry.

2. SKSE later captures the same real function address in DICreate_RealFunc and
   rewrites Skyrim's IAT to its own wrapper.

3. When SKSE's wrapper calls DICreate_RealFunc, execution still reaches the
   MinHook detour at the real function entry.

4. GZFX receives the real IDirectInput8 object returned under SKSE's wrapper and
   hooks its real CreateDevice method.

5. SKSE FakeDirectInput::CreateDevice later calls the real object's
   CreateDevice; GZFX observes GUID_SysMouse and hooks the real mouse device.

6. SKSE FakeDirectInputDevice::GetDeviceState / GetDeviceData later call the
   real mouse device methods; GZFX intercepts those lower-level calls.

7. With the GZFX menu open, GZFX forwards the real mouse packet to the menu and
   zeros/suppresses it before SKSE's wrapper and Skyrim consume it.

Thus GZFX does NOT replace or bypass SKSE's DirectInput wrapper. It operates
underneath it on the real system DirectInput implementation.

This ordering is desirable because SKSE continues to own its normal input
processing while GZFX temporarily owns only the system mouse stream when its
overlay is open.

The SKSE source also documents kMessage_InputLoaded as being sent only after
game input is loaded and immediately before main-menu initialization, further
confirming that plugin Load is the correct early arm point.
