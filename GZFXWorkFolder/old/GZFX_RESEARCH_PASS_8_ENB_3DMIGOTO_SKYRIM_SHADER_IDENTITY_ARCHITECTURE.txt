======================================================================
1. EXECUTIVE VERDICT
======================================================================

This research materially sharpens Research Pass 7.

The useful lesson from ENB is NOT:

    "copy ENB's proprietary implementation"

and it is NOT:

    "turn GZFX into another d3d11.dll proxy."

The useful lesson is that a mature graphics framework must maintain stable
identity across the rendering stack.

The architecture repeatedly seen across ENB's shipped SDK/shaders, 3Dmigoto,
ReShade, Community Shaders, PureDark's public Skyrim Upscaler, Nukem9's public
Skyrim shader tooling, and GZFX's own successful field evidence is:

    1. intercept graphics-device creation early;
    2. know the primary device/context/swapchain from birth;
    3. assign stable identities to shaders/resources when they are created;
    4. track current D3D state continuously;
    5. know which subsystem owns every injected command list;
    6. anchor generic D3D activity to game-specific semantic phases;
    7. run custom graphics work at an intentional stage, not simply "at Present";
    8. restore/contain state so injected work cannot silently corrupt Skyrim;
    9. use engine semantics and D3D evidence to cross-validate one another.

GZFX already owns a surprising amount of this architecture.

It already has:

    - dinput8 bootstrap;
    - SkyrimSE.exe IAT interception for D3D11/DXGI creation;
    - primary device/context/swapchain discovery;
    - immediate-context execution interception;
    - semantic resource authority;
    - detailed resource lineage;
    - deferred-context recording;
    - command-list execution service;
    - stage scheduler;
    - GPU work recorded on deferred contexts;
    - explicit state restoration behavior;
    - caller-module code in the experimental creation lane;
    - resource birth records;
    - shader bytecode hashing code.

The critical gap is that GZFX's strongest stable creation-time identity lane is
currently disabled in normal field builds behind:

    GZFX_EXPERIMENTAL_DEVICE_CREATION_HOOKS

As a consequence, normal telemetry often substitutes a runtime COM pointer when
a stable shader bytecode hash is unavailable.

That has forced late renderer research to repeatedly rediscover the same shader
families from volatile pointer values and resource shapes.

Research Pass 8 therefore recommends:

    DO NOT replace GZFX's architecture with ENB/3Dmigoto wrappers.

Instead:

    PROMOTE a hardened creation-time identity registry
    +
    COMPLETE command-list ownership
    +
    ADD Skyrim engine semantic anchors from Research Pass 7
    +
    KEEP existing D3D state/resource cartography as independent proof.

This is the shortest path from today's forensic renderer to a stable native
graphics framework.

6. ENB SHIPPED FX FILES REVEAL A MULTI-STAGE SEMANTIC POST STACK
======================================================================

The editable shader package is more useful architecturally than guessing from

ENB exposes separate stages with different semantic inputs and color domains.

----------------------------------------------------------------------
6.1 ENBEFFECTPREPASS.FX
----------------------------------------------------------------------

The shipped prepass operates with:

    HDR scene color
    scene depth
    mask / skinned-object / SSS information
    temporal/noise information
    screen/frame state.

The readme states this shader was added as a pre-pass and executes before
enbdepthoffield.fx.

This proves a deliberately exposed pre-DOF HDR processing stage.

----------------------------------------------------------------------
6.2 ENBDEPTHOFFIELD.FX
----------------------------------------------------------------------

The DOF shader consumes:

    current color
    original color
    scene depth
    focus/aperture state
    adaptation state.

Its own comments define ordered internal techniques such as aperture/focus
steps.

This is an explicit semantic effect, not a generic post-Present filter.

----------------------------------------------------------------------
6.3 ENBADAPTATION.FX
----------------------------------------------------------------------

The adaptation shader exposes:

    current adaptation texture
    previous adaptation texture

and a downscale / temporal adaptation structure.

This independently corroborates why GZFX sees a tiny HDR history/reduction
family in Skyrim/late-post work.

It does NOT prove that ENB's exact adaptation algorithm equals Skyrim's
vanilla reduction chain.

It proves that persistent temporal exposure/adaptation state is a first-class
renderer concept in a mature Skyrim graphics framework.

----------------------------------------------------------------------
6.4 ENBBLOOM.FX / ENBLENS.FX
----------------------------------------------------------------------

The shipped bloom/lens files expose:

    HDR color
    original scene
    scene depth
    aperture/adaptation-related state
    sun/lens-specific inputs
    multiple temporary render targets at descending resolutions.

This is another strong demonstration that a graphics framework needs a
persistent resource graph, not merely one source texture at Present.

----------------------------------------------------------------------
6.5 ENBEFFECT.FX
----------------------------------------------------------------------

The main effect shader documents HDR color inputs and contains the main
color/tonemap-style transformation path.

It also contains an ORIGINALPOSTPROCESS path.

ENB's 0.309 readme states the early Skyrim SE implementation was primarily
intended to remove the original game post processing and replace it with the
custom enbeffect.fx path or another post processor.

Later versions add multipass support and many additional renderer features.

Research conclusion:

    the main ENB post stage sits inside a renderer ownership model,
    not outside Skyrim as an arbitrary overlay.

----------------------------------------------------------------------
6.6 ENBEFFECTPOSTPASS.FX
----------------------------------------------------------------------

The post-pass explicitly documents LDR color input/output formats while still
providing scene depth.

This gives ENB a distinct post-tonemap/post-main-effect domain.

That distinction is directly relevant to GZFX's unresolved:

    PostTonemapPreUi

boundary.

----------------------------------------------------------------------
6.7 ENBUNDERWATER.FX
----------------------------------------------------------------------

The underwater stage documents:

    LDR scene color
    scene depth
    underwater mask

and supports its own multipass effects.

Again, the architecture is semantic:

    underwater is not inferred because "some shader happened near water";

9. 3DMIGOTO: HOW A GENERIC D3D11 FRAMEWORK BUILDS STABLE IDENTITY
======================================================================

3Dmigoto is public source and therefore gives a clean architecture reference.

Its D3D11 wrapper loads/resolves the real D3D11 implementation and inserts
wrapper objects.

Important public behaviors include:

    wrapped device;
    wrapped immediate context;
    wrapped deferred contexts;
    swap-chain/DXGI handling;
    shader creation interception;
    shader binding interception;
    resource/state tracking;
    frame analysis;
    shader replacement.

----------------------------------------------------------------------
9.1 Deferred context creation
----------------------------------------------------------------------

3Dmigoto's HackerDevice::CreateDeferredContext:

    calls the real device;
    receives the real deferred context;
    creates a HackerContext wrapper;
    returns/hooks that wrapper.

This is the same architectural problem GZFX solved in 0.0.25 with deferred
context vtable recording, though implemented differently.

----------------------------------------------------------------------
9.2 Shader identity at creation
----------------------------------------------------------------------

3Dmigoto intercepts CreateVertexShader / CreatePixelShader / other stage
creation through a common CreateShader path.

It computes a hash from the shader bytecode and records:

    shader object -> stable shader hash.

Its public code supports several hash approaches.

Particularly relevant is a bytecode-oriented hash that can select meaningful
DXBC sections such as:

    SHDR / SHEX
    input signatures
    output signatures
    patch constant signatures

instead of treating a runtime COM pointer as the shader's identity.

This is a major lesson for GZFX.

----------------------------------------------------------------------
9.3 Handle reuse is treated as real
----------------------------------------------------------------------

3Dmigoto explicitly cleans shader maps when a shader object handle is reused.

This matches the lesson GZFX already learned for command-list pointer reuse:

    raw pointer identity is not historical identity.

Stable content identity plus generation/creation identity is required.

16. BUT NORMAL GZFX FIELD BUILDS DISABLE THAT LANE
======================================================================

AttachDevice() currently checks:

    GZFX_EXPERIMENTAL_DEVICE_CREATION_HOOKS

If the variable is not enabled:

    g_creationInterceptionEnabled = false
    and the function returns without replacing the device vtable.

A source comment explicitly says:

    execution-level cartography does not require device creation interception;
    the creation lane remains experimental until isolated proof;
    default field builds keep it disabled.

That was a defensible earlier safety decision.

It is no longer a good permanent architecture.

The 0.0.24/0.0.25 campaigns demonstrated the cost:

    runtime pointer identities repeatedly masquerade as shader identities;
    cross-run shader correlation is weak;
    engine-pass recognition must rediscover structures from dimensions and
    resource graphs;
    field shader pointers are useful only inside one process.

The next architecture should NOT simply flip the experimental environment
variable on and declare victory.

It should extract the useful creation-identity pieces into a hardened,
production-quality subsystem with explicit acceptance tests.

17. CURRENT TELEMETRY HAS A SHADER IDENTITY TYPE ERROR
======================================================================

This is subtle and important.

PassTelemetry has a field named:

    shaderHashes[]

But BuildPassTelemetryLocked currently writes:

    bytecode hash, if creation interception captured one;

otherwise:

    canonical shader object pointer/identity.

Therefore the same telemetry column can mean either:

    content identity

or:

    process-local COM identity.

This is why field values such as:

    0x25ECC9...

were correctly treated as runtime shader pointers and never as contracts.

The field name is semantically overloaded.

The next blueprint should split this explicitly.

Recommended shader identity payload per stage:

    object_id
    object_generation / birth
    exact_bytecode_hash
    structural_bytecode_hash
    bytecode_bytes
    owner_module
    identity_confidence.

Telemetry must never silently substitute one identity domain for another.

18. RECOMMENDED SHADER FINGERPRINT MODEL
======================================================================

A stable GZFX shader record should include multiple fingerprints because they
serve different purposes.

A. Exact hash

    hash the complete DXBC blob.

Purpose:

    exact shader-build identity.

Current GZFX FNV-1a full-blob hash can serve this role.

B. Structural/program hash

    hash executable/signature DXBC sections while excluding volatile compiler
    metadata.

Public 3Dmigoto demonstrates this approach using code/signature sections.

Purpose:

    survive irrelevant compiler/debug metadata changes while still detecting
    functional shader changes.

GZFX should independently implement its own parser/hasher.

C. Optional embedded DXBC identity

    where valid/available, record the DXBC embedded digest/header identity.

Purpose:

    another independent cross-check.

D. Reflection signature

Use D3DReflect when available to record bounded facts such as:

    shader stage/model;
    bound resource count;
    constant-buffer count;
    signature/resource layout hash.

Purpose:

    structural corroboration, not semantic naming.

All fingerprints should be immutable creation records.

======================================================================
19. SELF-CALIBRATING SKYRIM SHADER SEMANTICS
======================================================================

This is one of the strongest new architectural ideas from combining Pass 7 and
Pass 8.

GZFX does NOT need to ship an enormous hardcoded Skyrim shader database.

Instead:

    engine semantic anchor
    +
    creation-time stable shader fingerprint
    +
    D3D resource graph

can calibrate itself.

Example:

1. The verified Skyrim ISTemporalAA engine anchor fires.

2. GZFX records:
       engine event = ISTemporalAA enter
       current VS/PS/CS exact and structural fingerprints
       bound SRVs/RTVs/UAVs
       MOTION/depth semantic relationships
       output graph.

3. The same anchor exits.

4. GZFX now has a field-proven association:

       this shader-family fingerprint
       participates in Skyrim global TAA
       on this runtime.

5. Future frames/runs can use the fingerprint as a secondary fast recognizer.

6. The engine anchor remains the primary authority when available.

This avoids both bad extremes:

    hardcoding volatile shader pointers;

and:

    maintaining a giant manually curated address/hash database as sole truth.

The same calibration can apply to:

    HDR downsample/adaptation;
    tonemap;
    water TAA;
    water blend;
    reflection apply;
    image copies;
    shadow/image-space phases.

======================================================================
20. RESOURCE BIRTH IDENTITY SHOULD ALSO BECOME FIRST-CLASS
======================================================================

PureDark's public upscaler independently demonstrates why resource creation
matters.

It discovers motion/depth/other targets at CreateTexture2D time because later
renderer initialization can be too late.

GZFX currently reconstructs many resources from bound views and shapes, which
has worked impressively well.

But creation-time records add:

    true birth order;
    creator module;
    original descriptor;
    stable generation;
    ability to distinguish object-address reuse;
    ability to correlate named engine target creation later.

Recommended resource identity:

    canonical object id
    birth generation
    creator module
    descriptor hash
    dimensions/format/binds
    debug name if present
    first semantic use
    last semantic use.

Do NOT use resource creation shape alone as semantic truth.

Use it as one axis of evidence.

======================================================================
21. ENB STATE-TRACKING LESSON VS GZFX DEFERRED EXECUTION
======================================================================

ENB's SDK emphasizes that wrapped D3D objects track changes so state can be
restored.

GZFX does not need to copy that exact implementation.

GZFX has a potentially cleaner equivalent for its own injected graphics work:

    record work on deferred contexts;
    execute through renderer_execution_service;
    explicitly choose RestoreContextState behavior;
    preserve ownership tags;
    keep Skyrim's immediate state isolated.

This is already a good architecture.

The problem is not that GZFX lacks all state containment.

The problem is that some GZFX paths bypass the central service.

Examples already identified:

    visible_pass
    resource_intelligence diagnostics
    semantic_probe diagnostics

can directly call ExecuteCommandList.

Research recommendation:

    make renderer_execution_service the single ownership/state-execution
    gateway for every GZFX-produced command list.

That gives GZFX the same architectural benefit ENB advertises:

    custom graphics work is attributable and state-safe.

without requiring a full COM-wrapper rewrite.

======================================================================
23. WHY GZFX SHOULD NOT SWITCH TO A FULL PROXY/WRAPPER DESIGN
======================================================================

ENB and 3Dmigoto prove that full wrappers work.

They do not prove that wrappers are the best next step for GZFX.

GZFX already has:

    dinput8 bootstrap;
    early executable-IAT D3D interception;
    proven primary renderer acquisition;
    MinHook;
    per-context interception;
    deferred work isolation;
    semantic authority;
    resource lineage.

A full ID3D11Device/Context/DXGI wrapper rewrite would add:

    COM QueryInterface complexity;
    interface-version upgrade handling;
    reference-counting hazards;
    proxy chaining complexity;
    compatibility risk with other graphics layers;
    large new test surface;

without directly solving the current semantic blocker.

The better plan is:

    retain current delivery/interception model;
    centralize identity and ownership;
    harden only the creation methods needed for identity;
    add verified Skyrim engine anchors.

This gets the architectural benefit with substantially less disruption.

24. HARDENING THE CURRENT EXPERIMENTAL DEVICE-CREATION LANE
======================================================================

Research recommendation for the next blueprint:

Do NOT enable the entire old experimental device vtable lane blindly.

Split it into explicit capabilities.

CAPABILITY A — ShaderIdentityCreation

Intercept only shader creation functions:

    CreateVertexShader
    CreatePixelShader
    CreateGeometryShader
    CreateGeometryShaderWithStreamOutput
    CreateHullShader
    CreateDomainShader
    CreateComputeShader.

Record identity only.

No replacement.
No mutation.
No shader-bytecode modification.

CAPABILITY B — ResourceBirthIdentity

Intercept only resource creation required for provenance:

    CreateBuffer
    CreateTexture1D
    CreateTexture2D
    CreateTexture3D.

Record identity only.

No descriptor modification.

CAPABILITY C — DeferredContextBirth

Coordinate with the already-proven 0.0.25 deferred cartography attach path.

Each capability must have:

    independent installation result;
    byte/vtable validation;
    conflict detection;
    counters;
    fail-closed fallback;
    harness coverage.

This is much safer than one broad "experimental device hooks" switch.

======================================================================
25. HOOK INSTALLATION / COMPATIBILITY STRATEGY
======================================================================

The primary renderer device is already captured by GZFX's D3D11 creation IAT
hook.

Creation identity hooks should therefore be installed immediately after the
real device is returned and before Skyrim receives control back from the
creation call.

This reproduces the important timing property seen in ENB/PureDark:

    observe creation before important resources/shaders are born.

Implementation options should be evaluated in BLUEPRINT:

OPTION 1:
    validated per-instance vtable clone for only selected creation methods.

Pros:
    already exists in GZFX;
    isolated to primary device instance.

Cons:
    hook-chain/conflict concerns.

OPTION 2:
    MinHook selected underlying method targets.

Pros:
    existing library;
    can chain original target.

Cons:
    global/shared method target;
    more care with multiple devices/hooks.

OPTION 3:
    full COM wrapper.

Not recommended for the next wave.

Whichever option is chosen must detect an already-modified target/vtable and
fail closed or chain safely.

======================================================================
26. SHADER REFLECTION SHOULD BE BOUNDED AND OFF THE HOT PATH
======================================================================

ENB's imports include D3DReflect/D3DDisassemble.

3Dmigoto performs bytecode analysis.

GZFX can capture useful shader structure without turning every draw into a
disassembler.

At Create*Shader time only:

    calculate hashes;
    optionally run D3DReflect once;
    store bounded structural metadata.

Do NOT disassemble every shader during gameplay.

If human-readable disassembly is ever needed for a specific unknown family:

    dump it once as a targeted diagnostic artifact.

Creation-time work is naturally amortized and dramatically cheaper than
per-draw analysis.

27. ENGINE SEMANTICS + SHADER IDENTITY IS STRONGER THAN EITHER ALONE
======================================================================

Research Pass 7 proposed engine anchors.

Research Pass 8 now explains how to make them durable.

Engine anchor alone:

    tells us WHAT Skyrim says it is doing.

Shader identity alone:

    tells us WHICH GPU program is executing.

Resource graph alone:

    tells us WHAT data flows through it.

Together:

    engine semantic
    +
    stable shader fingerprint
    +
    resource inputs/outputs
    +
    timing/order

provides a much stronger renderer contract.

Acceptance rule example:

    BeforeGlobalTAA is locked only if:

        verified ISTemporalAA engine entry occurs;
        stable shader fingerprint family is observed;
        MOTION is read;
        MAIN_DEPTH_CURRENT is read;
        current/history color is read;
        expected temporal outputs are written;
        ordering is consistent across field environments.

No single pointer or texture shape is enough.

31. DO NOT BUILD A STATIC SHADER HASH CONTRACT
======================================================================

Stable shader hashes are powerful.

They are not eternal semantic truth.

A Bethesda update, compiler change, modded shader, Community Shaders, or future
GZFX ownership layer can change bytecode.

Therefore:

    hash -> semantic

must be version-scoped and evidence-backed.

Use hashes as:

    fast recognizers;
    cross-run correlation;
    contradiction detection.

Do not make:

    "hash X always means TAA"

the sole contract.

Primary authority remains:

    engine semantic anchor
    +
    verified resource behavior.

======================================================================
32. IMPORTANT COMPATIBILITY ADVANTAGE OF GZFX'S CURRENT DELIVERY MODEL
======================================================================

ENB's d3d11 proxy architecture is powerful, but a local graphics-DLL proxy is a
natural collision point with:

    ReShade;
    overlays;
    upscalers;
    other D3D wrappers.

ENB's own readme warns that overlays/capture tools can interfere.

GZFX's dinput8 bootstrap avoids claiming the d3d11 filename.

If GZFX can achieve complete identity through:

    early IAT interception
    +
    narrow validated device/context hooks
    +
    engine anchors

then it can retain a potentially cleaner compatibility position.

Therefore:

    do not change bootstrap architecture merely because ENB uses d3d11.dll.

The lesson is interception timing and persistent identity, not the filename.

36. FINAL RESEARCH VERDICT
======================================================================

The deeper ENB investigation does NOT tell GZFX to imitate ENB's binary.

It tells us why the current GZFX cartography became unnecessarily difficult.

We already intercept enough of D3D11.

We have been missing stable, authoritative identity.

The most valuable principles to carry into the next BLUEPRINT are:

    stable shader identity from creation;
    stable resource provenance from creation;
    complete GZFX command-list ownership;
    explicit real Present epochs;
    verified Skyrim engine semantic anchors;
    cross-correlation between engine semantics and D3D behavior.

The striking part is that GZFX already contains the beginning of nearly every
one of these systems.

The next wave is therefore not a renderer rewrite.

It is a consolidation / promotion wave that turns scattered forensic
capabilities into one authoritative renderer identity layer.

If implemented and field-validated correctly, this should allow GZFX to stop
asking:

    "what anonymous pass might this be?"

and start answering:

    "Skyrim entered ISTemporalAA; these exact stable shaders executed; these
    semantic resources were read; these outputs were produced; this happened
    before UI and before the actual DXGI Present."

That is the level of renderer ownership required before GZFX resumes the
graphics-feature roadmap.
