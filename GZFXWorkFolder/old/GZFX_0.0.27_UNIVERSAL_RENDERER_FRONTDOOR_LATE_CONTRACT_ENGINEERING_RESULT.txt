    D3D11CoreCreateDevice

    store module handle
    DisableThreadLibraryCalls

It does NOT:

    LoadLibrary GZFX

On a real application D3D create call:

    call real System32 D3D11 first
    ->
    receive real device/context/swapchain
    ->
    initialize GZFX outside loader lock
    ->
    explicitly attach the real primary objects
    ->
    return the unchanged real objects/HRESULT to the application.

This closes the 0.0.26 timing gap where dinput8 could lazy-load GZFX only after
core renderer resources already existed.

======================================================================
5. STARTUP REENTRANCY SAFETY
======================================================================

A startup-order hazard was found during implementation.

Possible order:

    dinput8 loads GZFX first
    ->
    GZFX_Initialize begins
    ->
    renderer_forensics creates a temporary WARP device
    ->
    WARP call re-enters local d3d11 proxy
    ->
    proxy could recursively call GZFX_Initialize
    ->
    same std::call_once could deadlock.

Repair:

    GZFX exports initialization state:

        0 not started
        1 initializing
        2 ready
        3 failed

    d3d11 proxy checks that state before initialization/attach.

If state=1:

    do not recursively initialize;
    forward the temporary D3D request;
    do not attach temporary WARP device as primary.

Primary attach is permitted only when state=2.

Both startup orders are now exercised by CI:

    GZFX-first existing harnesses
    D3D-first new front-door harness.

A 30-second CTest timeout bounds front-door deadlock detection.
