The high tail is dominated by intermittent depth-tail work and cannot be treated
as a clean release benchmark. It does prove the current architecture has
meaningful synchronization/work spikes.

Current cost topology is structurally poor for product expansion:

    Wave3 owns geometry/history preparation;
    AV2 owns ambient visibility;
    ambient_depth owns an additional half-resolution analyze/temporal/filter/
    composite sequence;
    scene_effects performs another full-resolution copy + pass + copy;
    telemetry and diagnostic capture add independent overhead.

Adding every missing feature as another isolated executor would multiply
full-resolution copies, state transitions, history stores, resource allocations
and synchronization points.

That architecture is rejected.

8. ARCHITECTURAL CONCLUSIONS
======================================================================

The next renderer must be organized around shared stage products:

    geometry/depth/motion/normal inputs;
    ambient visibility and indirect;
    one HDR scene source;
    one luminance/bloom pyramid;
    one exposure history;
    one reusable full-resolution ping-pong pair;
    one current/previous temporal registry;
    one ordered effect graph;
    one settings revision;
    one timing/diagnostic ledger.

Effects must declare:

    required stage;
    required semantic inputs;
    output semantic;
    temporal history ownership;
    quality tier;
    neutral behavior;
    reset conditions.

They must not each create a private renderer, private scene copy, private
scheduler or private interpretation of the same Skyrim resource.

The first large recovery wave is authorized to implement, together:

    product master switch;
    shared quality tiers;
    manual and automatic exposure;
    eye adaptation;
    bloom/glow and lens dirt;
    pre-tonemap shaping;
    color controls;
    DoF;
    motion blur;
    depth fog;
    vignette;
    film grain;
    chromatic aberration;
    sharpening;
    letterbox/pillarbox;
    bounded integrated timing/stage logs;
    built-in looks and custom profile lifecycle where safely achievable.

Native shadows, sky/weather, water/reflections and material replacement remain
separate native-domain work because they require distinct engine-stage
ownership, not because the project should return to tiny feature probes.

9. HBAO FLICKER / PERFORMANCE DISPOSITION
======================================================================

The HBAO flicker around the character is recorded as a real defect.

Likely contributing dimensions to test later:

    very large radius mapping:
        setting 96 -> world radius 822.857

    highest workload:
        4 slices x 8 steps

    stochastic per-frame horizon sampling;
    temporal rejection/disocclusion around animated geometry;
    depth/normal instability near the player;
    independent AV2 and Wave3 history behavior.

No field evidence currently justifies one exact root-cause claim.

The owner explicitly deprioritized this defect until the broad pipeline is
landed. The unified graph must preserve diagnostics needed to repair it later,
but this wave must not be derailed into another HBAO-only loop.
