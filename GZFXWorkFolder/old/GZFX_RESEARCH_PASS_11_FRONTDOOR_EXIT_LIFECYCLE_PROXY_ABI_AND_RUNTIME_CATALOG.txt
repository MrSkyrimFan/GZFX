2. DOCUMENTED D3D11 FRONT-DOOR SURFACE
======================================================================

Microsoft publicly documents:

    D3D11CreateDevice
    D3D11CreateDeviceAndSwapChain

as D3D11.dll entry points.

Microsoft also documents:

    D3D11On12CreateDevice

as the D3D11-on-D3D12 interoperability entry point.

Public Microsoft references:

    https://learn.microsoft.com/windows/win32/api/d3d11/nf-d3d11-d3d11createdevice
    https://learn.microsoft.com/windows/win32/api/d3d11/nf-d3d11-d3d11createdeviceandswapchain
    https://learn.microsoft.com/windows/win32/api/d3d11on12/nf-d3d11on12-d3d11on12createdevice

ReShade 6.8 public export definition exposes these three D3D11 entry points:

    D3D11CreateDevice
    D3D11CreateDeviceAndSwapChain
    D3D11On12CreateDevice

Reference:

    https://github.com/crosire/reshade/blob/v6.8.0/res/exports.def

ReShade's public D3D11On12 implementation forwards/interposes the documented
interop path:

    https://github.com/crosire/reshade/blob/v6.8.0/source/d3d11/d3d11on12.cpp

Research conclusion:

    GZFX should include D3D11On12CreateDevice in its public proxy contract.

3. UNDOCUMENTED D3D11CORE EXPORTS
======================================================================

0.0.27 currently exports:

    D3D11CoreCreateDevice
    D3D11CoreCreateLayeredDevice
    D3D11CoreGetLayeredDeviceSize
    D3D11CoreRegisterLayers

These are not the normal public application contract.

Historical 3Dmigoto's public d3d11Wrapper.def demonstrates that the old internal
d3d11.dll surface is substantially larger and ordinal-sensitive.

Its list includes:

    D3DKMT*
    OpenAdapter10
    OpenAdapter10_2
    D3D11Core*
    performance exports
    D3D11On12CreateDevice

and explicitly documents historic ordinal complications.

Reference:

    https://github.com/bo3b/3Dmigoto/blob/master/DirectX11/d3d11Wrapper.def

Therefore GZFX's current four D3D11Core functions are NOT a truthful full
compatibility implementation of the internal D3D11 ABI.

Research recommendation:

    remove the partial undocumented Core export contract;
    expose the documented/public three D3D11 entry points;
    forward them to absolute System32 d3d11.dll.

This is deliberately narrower and more truthful.

If future field evidence proves Skyrim or a required Windows component needs a
specific internal export through the local proxy, add it from measured evidence
with correct ABI/ordinal behavior.

Do not preemptively emulate a historic internal surface.

4. D3D11ON12 MUST NOT CLAIM SKYRIM PRIMARY
======================================================================

D3D11On12CreateDevice creates a D3D11 interface over a pre-existing D3D12
device/queue.

It is useful for D2D/UI/interoperability components and does not imply:

    "this is Skyrim's primary native D3D11 renderer."

Therefore the 0.0.28 proxy should:

    forward D3D11On12CreateDevice faithfully;

    record a compact startup/proxy event if useful;

    NOT initialize/attach it as GZFX's primary Skyrim renderer.

The Skyrim primary remains the qualified D3D11CreateDevice or
D3D11CreateDeviceAndSwapChain path.

5. PRIMARY DEVICE QUALIFICATION
======================================================================

A mature renderer front door cannot attach the first successful device blindly.

ReShade 6.8 public D3D11 logic explicitly avoids treating WARP/reference devices
as normal proxied application renderers and also detects Microsoft Basic Render
Driver.

Reference:

    https://github.com/crosire/reshade/blob/v6.8.0/source/d3d11/d3d11.cpp

GZFX should independently implement a smaller primary-candidate rule.

Candidate inputs:

    original DriverType;
    created device adapter description;
    calling module;
    swapchain output window where available.

Real Skyrim candidate should be rejected if:

    driver type == WARP;
    driver type == REFERENCE;
    driver type == SOFTWARE;
    driver type == NULL;

or if the actual adapter is:

    Microsoft Basic Render Driver
        VendorId = 0x1414
        DeviceId = 0x008C

or if a supplied swapchain output window belongs to another process.

Strong additional signal:

    calling module == main executable module.

Because Skyrim's normal D3D create path is expected from SkyrimSE.exe, GZFX can
use main-executable provenance as a primary-acceptance criterion.

If a future real field build proves a legitimate Skyrim renderer creation comes
through another module, update from evidence.

Tests need WARP, so provide a test-only environment override:

    GZFX_TEST_ALLOW_SOFTWARE_PRIMARY=1

The override must never be used by normal product execution.

Telemetry should explain rejection reasons.

6. D3D-FIRST VS GZFX-FIRST STARTUP PARITY
======================================================================

There are two legitimate startup orders.

PATH A — D3D FIRST

    local d3d11 proxy
    ->
    real device creation
    ->
    GZFX load/init
    ->
    GZFX_AttachPrimaryD3D11
    ->
    application receives primary objects.

0.0.27 tests this.

PATH B — DINPUT / GZFX FIRST

    dinput8
    ->
    GZFX load/init
    ->
    ArmD3D11LifecycleProbe
    ->
    Skyrim D3D IAT call
    ->
    HookD3D11CreateDevice[AndSwapChain].

Current PATH B attaches:

    pipeline_cartography
    renderer_execution_service

but does not call:

    renderer_forensics::AttachPrimaryRendererObjects.

Therefore the two startup orders are not behaviorally equivalent before first
Present.

Research recommendation:

    successful d3d11_lifecycle primary creation must call the same explicit
    renderer-forensics attach API.

One primary-attachment implementation should govern both startup orders.

Add a test where:

    GZFX loads first;
    D3D device/swapchain is created;
    a context operation occurs BEFORE Present;
    renderer-forensics evidence proves that operation was observed.

7. DLLMAIN / PROCESS-EXIT CONSTRAINTS
======================================================================

Microsoft states DllMain runs under the loader lock and recommends minimal work.

It specifically warns against:

    LoadLibrary / LoadLibraryEx from DllMain;
    synchronizing with other threads in DllMain.

Reference:

    https://learn.microsoft.com/windows/win32/Dlls/dynamic-link-library-best-practices

This validates 0.0.27's minimal d3d11 DllMain.

It also means telemetry worker-thread shutdown must NOT be moved into
DLL_PROCESS_DETACH.

======================================================================
8. CURRENT Atexit APPROACH IS THE WRONG FIELD CLOSURE CONTRACT
======================================================================

Important source fact:

    runtime.cpp registers std::atexit in non-test processes when telemetry
    initializes.

Important test fact:

    the front-door and telemetry harnesses call GZFX_Shutdown manually.

Therefore current CI does NOT prove the real automatic process-exit path.

Important field fact:

    0.0.25 and 0.0.26 normal Skyrim sessions repeatedly lacked
    telemetry_session_complete.txt.

The field evidence therefore shows the current automatic shutdown mechanism is
not yielding reliable completion proof.

The telemetry shutdown function:

    writes files;
    wakes a writer thread;
    joins that thread;
    flushes final output.

This must happen while normal process threads still exist.

Microsoft's ExitProcess documentation states that process exit subsequently
terminates other threads and then invokes DLL process-detach entry points.

References:

    https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-exitprocess
    https://learn.microsoft.com/windows/win32/procthread/terminating-a-process

Research conclusion:

    the clean interception point is BEFORE the real ExitProcess begins its
    teardown sequence.

9. RECOMMENDED PROCESS-EXIT LIFECYCLE
======================================================================

Install a process-level ExitProcess detour from the long-lived d3d11 bootstrap.

Why bootstrap, not GZFX.dll:

    test harnesses can FreeLibrary(GZFX.dll);

    a detour target whose thunk lives in an unloaded GZFX module would be unsafe;

    local d3d11.dll is a process-level graphics bootstrap expected to remain
    loaded through application lifetime.

Implementation concept:

    first relevant D3D front-door initialization
    ->
    initialize bootstrap MinHook
    ->
    hook resolved ExitProcess target
    ->
    store original trampoline.

Hook:

    atomic once guard
    ->
    emit process_exit_intercepted where possible
    ->
    if GZFX loaded and initialization state ready:
        call exported GZFX_Shutdown()
    ->
    call original ExitProcess(exitCode)

Never return from the detour.

Remove the DLL std::atexit telemetry-shutdown registration to avoid two competing
lifecycle contracts.

This is NOT a DllMain cleanup hook.

10. NATURAL-EXIT ACCEPTANCE TEST
======================================================================

Current tests manually call GZFX_Shutdown and therefore cannot validate the
real process lifecycle.

Add parent/child acceptance.

Child:

    uses local GZFX d3d11 bootstrap;
    creates a device;
    allows GZFX/telemetry to initialize;
    emits some renderer activity;
    returns normally from main WITHOUT calling GZFX_Shutdown.

Parent:

    CreateProcess child;
    waits for child exit;
    validates newest child telemetry session contains:

        session_close_state.txt
            state=complete

        telemetry_session_complete.txt
            status=complete

This is the field-equivalent closure proof.

Bound the child test with a timeout.

11. STARTUP TRACE MUST BE PROCESS-SCOPED
======================================================================

Current:

    Diagnostics/renderer_startup.csv
    append mode across process launches.

Required:

On first Record() in a process:

    truncate/create the file;
    write header;
    sequence starts at 1.

Each row should include:

    pid
    sequence
    qpc
    thread
    event
    result
    pointer_a
    pointer_b.

Later calls in the same process append.

This ensures field review never combines stale launch history.

Add a test that pre-seeds stale content, starts a new process, and proves the new
startup file does not contain the stale marker.
