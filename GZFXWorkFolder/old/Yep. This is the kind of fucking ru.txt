# 6. Stock temporal AO is now much more strongly proven

This is one of my favorite findings from the saturation run.

The stock RawAO stage reads:

- CameraZ
- current native normal
- motion vectors
- previous AO/history

and alternates two full-resolution RGBA8 targets frame-to-frame.

Then two more full-resolution RGBA8 filtering passes follow it.

So the sequence is structurally:

**CameraZ + normal + motion + previous AO → new RawAO/history → filter 1 → filter 2**

And because we now have many moving and stationary captures, we can test whether that "history" behavior actually reacts to motion.

It does.

The amount the two RawAO history surfaces differ correlates strongly with motion activity.

Approximate correlations:

| Comparison | Correlation |
|---|---:|
| Raw-history difference magnitude vs motion magnitude | **~0.73** |
| Raw-history changed-area vs motion-active area | **~0.89** |
| Raw-history changed-area vs its own overall difference | **~0.99** |

That is **very strong field evidence** that these are genuine temporally reprojected/history-bearing AO surfaces, rather than two random scratch buffers that happen to alternate.

### Verdict

**Stock temporal RawAO family: FIELD IDENTIFIED.**

**Two-pass AO filtering immediately afterward: VERY STRONG / essentially locked at family level.**

This is especially important when we later redesign GZFX temporal AO. Skyrim already has infrastructure doing a lot of the things we tried to reinvent poorly.

# 8. We caught one of our previous conclusions being too strong

This is exactly why you wanted XForge-style discipline.

PR21 documentation promoted the **640×360 RGBA16F temporal ping-pong** as belonging to the volumetric temporal/projection chain.

That interpretation is now **too narrow**.

The compute shader:

`0x278CB7C26D0`

runs **three times in every capture**, including every interior.

But the actual exterior 3D volumetric system is completely absent indoors.

So this temporal pair **cannot be exclusively the exterior volumetric temporal system**.

It reads:

**main HDR + previous 640×360 history + motion**

and writes the alternate 640×360 history target.

Then another graphics pass consumes the new temporal surface.

Outdoors that consumer also sees the volumetric 3D resources.

Indoors the same broad stage survives **without those volumetric resources** and consumes a different reduced-lighting/environment set.

### Corrected verdict

It is a:

**cross-environment temporal reduced-lighting / image-space history stage**

Its **exact semantic purpose remains unresolved**.

And importantly:

It is **also not proven to be global scene TAA**. At 640×360 on a 2560×1440 render, the evidence does not support casually calling it Skyrim's main TAA history.

So:

**old "volumetric temporal" label gets demoted.**

**global Skyrim TAA remains unresolved.**

That is a real correction we need to carry into research and eventually the docs, but not yet. Repo stays untouched.

# 13. One probe defect remains

0.0.18 fixed canonical IDs in the **pipeline graph**.

But the semantic preview system still has an identity seam.

For example, capture 0001 has canonical pipeline identities like:

`scene = 0x2787CE5BC40`

while semantic-candidate output reports the underlying resource through a different interface pointer such as:

`scene = 0x2787CE5BD20`

They are the same underlying COM object reached through different interfaces, but the outputs don't currently provide a clean explicit crosswalk.

So:

**pipeline graph IDs and semantic-preview candidate IDs cannot always be directly joined by pointer string.**

I compensated during this review by using descriptors, known anchors, pass chronology, shader ownership and producer/consumer structure separately.

But this is a real probe-design defect.

There is a second issue:

**candidate rank is not semantic identity.**

"candidate 8" can be one AO surface outdoors and a different resource indoors because ranking changes.

Future diagnostic work should name previews by **structural landmark**, not merely "candidate 08."

Again: I have **not fixed either issue yet**, because that would violate the new workflow.
