Three real integration weaknesses remained.

A. PRELOAD-PHASE EXECUTABLE MUTATION

0.0.31/0.0.32 SKSEPlugin_Preload called:

    ArmEarlyGraphicsBootstrap
      -> ArmD3D11LifecycleProbe
         -> parse SkyrimSE.exe PE imports
         -> VirtualProtect D3D11/DXGI IAT slots
         -> replace imports

This happened during SKSE's capability-limited Preload phase, before Skyrim
global initializers.

The previous CI harness tested this against a synthetic harness executable, not
against the real SkyrimSE.exe 1.7.104 image.

B. DYNAMIC MICROSOFT VC++ RUNTIME DEPENDENCY

The 0.0.32 shipped DLL dynamically imported:

    MSVCP140.dll
    VCRUNTIME140.dll
    VCRUNTIME140_1.dll
    api-ms-win-crt-* runtime DLLs

A missing/incompatible runtime can make Windows LoadLibrary fail before GZFX
executes any logging code.

The GitHub Windows runner already contains the Visual Studio runtime, so the old
CI did not prove clean-machine loading.

C. COMMONLIB SKSE INITIALIZATION CONTRACT

0.0.32 linked CommonLibSSE-GG but did not call its supported:

    SKSE::Init(const SKSE::LoadInterface*, bool)

The pinned CommonLib implementation uses this entry point to initialize:

    REL::Module
    REL::IDDatabase
    CommonLib SKSE API storage/interfaces

0.0.32 instead touched selected REL state manually.

Without the failed user's old SKSE logs, no single one of A/B/C is claimed as
the sole proven root cause.

0.0.33 removes all three known loader/integration defects/risks coherently.

======================================================================
3. SKSE PRELOAD / LOAD REPAIR
======================================================================

SKSEPlugin_Preload remains exported for the official SKSE two-phase plugin
contract.

0.0.33 Preload now does ONLY:

    exact runtime/SKSE compatibility check
    mark preload entered
    record no graphics arm
    return true

Preload no longer:

    parses SkyrimSE.exe imports
    calls VirtualProtect on D3D/DXGI IAT slots
    installs renderer observation
    initializes CommonLib
    initializes runtime subsystems
    performs runtime filesystem setup

Renderer observation now arms in normal:

    SKSEPlugin_Load

before GZFX_Initialize.

GZFX_Initialize retains coherent subsystem ownership and its existing call_once
behavior.

New bridge evidence includes:

    preload_entered=true
    graphics_arm_phase=load
    early_graphics_armed=<true/false>

The CI front-door harness now explicitly asserts that Preload leaves the GZFX
runtime initialization state at zero and creates no D3D lifecycle diagnostics.

5. SELF-CONTAINED WINDOWS RUNTIME REPAIR
======================================================================

0.0.33 changes the MSVC/vcpkg build model from:

    x64-windows-static-md
    dynamic MSVC runtime (/MD)

to:

    x64-windows-static
    static MSVC runtime (/MT family)

CMake locks CMP0091 before project() and selects:

    MultiThreaded$<$<CONFIG:Debug>:Debug>

    MSVCP*.dll
    VCRUNTIME*.dll
    api-ms-win-crt-*.dll

The same gate proves required exports remain present.
