======================================================================
0. PURPOSE
======================================================================

This blueprint corrects the first implementation of the GZFX renderer
foundation after real-Skyrim evidence exposed three structural problems:

1. Resource identity was being treated as if it implied current semantic
   validity.

2. A physical depth texture with multiple in-frame roles was assigned one
   permanent semantic name.

3. Stage events were tied too closely to semantic discovery rather than to
   actual per-frame execution completion.

The corrected foundation must preserve what 0.0.19 proved good while removing
those static assumptions.

The objective of this revision is:

- close Wave 1 correctly;
- close Wave 2 correctly;
- establish safe runtime contracts for Wave 3;
- prevent future AO/GI from binding to stale or semantically wrong resources;
- give future effects real stage ownership instead of approximate timing.

Production AO/GI redesign remains paused until this corrected foundation
passes its real-Skyrim field gate.

2. CORE ARCHITECTURAL CORRECTION
======================================================================

The 0.0.19 semantic model was:

physical resource
->
one semantic identity

The corrected model is:

physical resource identity
+
current frame state
+
stage
+
content epoch
+
environment
->
semantic view

A single texture may hold different semantic content at different moments.

Therefore GZFX must stop treating a COM identity as a permanent semantic fact.

======================================================================
3. NEW REQUIRED CONCEPTS
======================================================================

The corrected foundation introduces four separate concepts.

----------------------------------------------------------------------
3.1 RESOURCE IDENTITY
----------------------------------------------------------------------

Persistent structural knowledge about a physical D3D11 resource.

Contains:

- canonical IUnknown identity
- generation
- descriptor
- format
- dimensions
- mip count
- array size
- bind flags
- first seen frame
- last seen frame
- confidence
- known structural roles

This record can survive across many frames.

It does NOT mean the resource is safe to consume now.

----------------------------------------------------------------------
3.2 FRAME AVAILABILITY
----------------------------------------------------------------------

Current-frame validity.

Contains at minimum:

- observed_this_frame
- produced_this_frame
- consumed_this_frame
- last_observed_frame
- last_produced_frame
- current_frame_available
- environment validity
- valid_from_stage
- valid_until_stage

A semantic broker query for a current-frame resource must fail closed if this
contract is not satisfied.

----------------------------------------------------------------------
3.3 SEMANTIC VIEW
----------------------------------------------------------------------

The meaning of a resource at a specific stage.

Examples:

MAIN_DEPTH_CURRENT

CAMERAZ_CURRENT

RAW_INDIRECT_CURRENT

VOLUMETRIC_PREVIOUS_DEPTH

POST_ZPREPASS_DEPTH_CURRENT


A Semantic View is what production effects request.

Effects do not directly request raw physical resources.

----------------------------------------------------------------------
3.4 CONTENT EPOCH
----------------------------------------------------------------------

A content epoch describes when one physical resource changes meaning after a
known producer/copy event.

The critical field-proven example:

same physical depth texture

Epoch A:
before current MAIN_DEPTH copy
=
previous-frame depth for volumetric temporal reprojection

Epoch B:
after current MAIN_DEPTH copy
=
current pre-water/post-z-prepass depth

The physical resource identity does not change.

The semantic content does.

8. NEW BOUNDARY: AFTER_OPAQUE_WORLD_MRT
======================================================================

This is required by the revised architecture.

Purpose:

identify the completion of the main opaque four-target world MRT before
stock CameraZ construction begins.

Why this boundary matters:

At this point GZFX should have access to:

- MAIN_HDR
- MAIN_DEPTH
- MOTION
- NORMAL_MASK_CURRENT
- AUXILIARY_RT3

with opaque world geometry for that stage already rendered.

This boundary is a better candidate for GZFX-owned screen-space analysis
snapshotting than the later exterior-only pre-water depth publication.

Detection requirement:

must be structural.

Do NOT:

- hardcode one ordinal;
- hardcode one shader pointer;
- assume one draw count.

Recommended state-machine concept:

1. main four-target MRT has been observed and active;
2. opaque-MRT activity is ongoing;
3. transition occurs away from main MRT into the known stock CameraZ producer;
4. emit AfterOpaqueWorldMRT once per frame before first CameraZ write.

This boundary should be proven first as a no-op execution landmark.

======================================================================
9. AFTER_CAMERAZ
======================================================================

0.0.19 behavior:
BROKEN

Reason:
event was tied to semantic promotion.

Correct contract:

AfterCameraZ fires once per applicable frame after the current frame's active
CameraZ hierarchy is fully produced.

Required algorithm:

- track active CameraZ identity;
- track mip writes for current frame;
- derive required mip coverage from descriptor;
- reset coverage on frame transition;
- observe mip writes;
- when required hierarchy completion condition is met:
  emit AfterCameraZ
  exactly once for that frame.

Important:

Promotion is separate.

CameraZ identity can be known for thousands of frames while the stage
completion event still fires once each frame.

Compute CameraZ paths:

If the engine uses a compute stage that creates multiple mips differently,
the scheduler must support an alternate structural completion rule.

Do not hardcode "12 draw calls" as the abstract contract.

21. PRODUCTION AO/GI DEPTH POLICY REVISION
======================================================================

Blueprint v1.0 treated stock CameraZ as a preferred hierarchy.

Revision 2 narrows that claim.

New policy:

Stock CameraZ is:

- trusted;
- useful;
- field-proven;
- useful for comparisons and stock-system mapping.

But production GZFX AO/GI should not automatically depend on stock CameraZ as
its final geometry hierarchy.

Reason:

public renderer work demonstrates that earlier z-prepass depth can omit
alpha-tested geometry and other later opaque content.

GZFX field evidence shows stock CameraZ is sourced from the early copy.

Therefore production AO/GI must evaluate:

GZFX-owned hierarchical depth
built from:
MAIN_DEPTH
at:
AfterOpaqueWorldMRT

This is now a planned Wave 3 responsibility.
