======================================================================
1. EXECUTIVE VERDICT
======================================================================

The 0.0.25 field session is useful and materially advances the diagnosis, but
it does NOT validate the four new late-stage promotions and does NOT yet expose
the dominant normal deferred command-list stream in the written detailed files.

The session proves two distinct implementation assumptions were wrong:

A. The HDR-reduction detector is too eager and stateful.
   It latches onto an earlier valid-looking MAIN_HDR -> RGBA16F low-resolution
   candidate and has no restart/backtracking path when that candidate does not
   develop into the real reduction chain.

B. Deferred-list telemetry is incorrectly coupled to the late-detail gate.
   The dominant non-GZFX command list executes after the current UiPresent
   stage timestamp. The detail gate has already switched off, so the recorder
   successfully recognizes the list internally but the telemetry transport
   intentionally discards its DeferredList/DeferredRun events.

The underlying renderer evidence did NOT disappear.

The known real late chain is still present throughout all active scene frames:

    full-resolution RGBA8 current image

Therefore the old late-stack discovery remains structurally real. The failed
0.0.25 promotion is a detector/timeline problem, not evidence that the prior

9. ROOT CAUSE #1 — HDR DETECTOR POISONING
======================================================================

Current source:

    src/render/semantic_authority.cpp

0.0.25 ObserveHdrReductionLocked() uses a single mutable chain state:

    hdrReductionStep
    hdrReductionLastIdentity
    hdrReductionLastWidth
    hdrReductionLastHeight

When step == 0, the first qualifying post-ambient pass that:

    reads MAIN_HDR
    writes RGBA16F
    is <= half-resolution

becomes the chain root.

Every later step must then:

    read hdrReductionLastIdentity
    AND
    strictly descend in area.

There is no:

    candidate set
    timeout
    restart
    backtracking
    replacement root
    completed-graph scoring.

Real Skyrim contains earlier valid-looking MAIN_HDR-consuming RGBA16F work
before the actual terminal reduction chain.

In ordinary active frames, an earlier 640x360 RGBA16F output qualifies as the
first root.

On representative frame 819, the earlier candidate is even more obvious:
one compute pass writes two RGBA16F outputs:

    160x90
    640x360

while reading MAIN_HDR.

Once the detector locks to one of these earlier candidates, the later true
640x360 -> 160x90 -> ... -> 2x2 chain cannot satisfy the strict
"consume my previous output and shrink from it" requirement.

The detector never recovers.

Therefore:

    hdrReductionComplete remains false
    ->
    BeforeTonemap is never eligible
    ->
    BeforeGlobalTAA is never eligible
    ->
    AfterGlobalTAA is never eligible.

This single failure naturally explains all four zero-count promoted stages.

DATA classification:

    STRONG ROOT-CAUSE FINDING

Required design correction should be researched before blueprinting. A robust
solution should not trust the first plausible reduction candidate.

12. ROOT CAUSE #2 — DEFERRED TELEMETRY GATE CLOSES TOO EARLY
======================================================================

Current telemetry_listener behavior:

OnDeferredList() and OnDeferredRun() return immediately when:

    full_pipeline_detail == false
    AND
    detailActive == false.

detailActive becomes true at:

    AfterAmbientScreenSpaceComposite

and becomes false at:

    UiPresent.

The dominant non-GZFX list executes AFTER the current UiPresent stage event.

For the dominant pointer:

    executions with matched UiPresent: 6,375
    executions after current-frame UiPresent: 6,375 / 6,375

QPC frequency:

    10,000,000 ticks/sec

QPC delay after current UiPresent:

    minimum: 676 ticks
    median:  922 ticks
    maximum: 2,591,777 ticks

Median delay:

    ~92.2 microseconds after the UiPresent telemetry event.

Therefore the detailed gate is off by the time the normal command list reaches:

    telemetry_listener::OnDeferredList()
    telemetry_listener::OnDeferredRun()

The deferred recorder recognizes it internally, increments listsExecuted, and
has zero opaque fallback, but the writer-side API intentionally returns
without enqueuing the list/run rows.

This is the direct reason the dominant deferred stream is absent from the CSV.

DATA classification:

    PROVEN GATING DEFECT / TIMELINE DESIGN DEFECT

13. IMPORTANT TIMELINE CORRECTION
======================================================================

The prior 0.0.24 interpretation called these events "Skyrim late deferred
command lists."

That wording is now too strong.

Current ownership code classifies a command list as:

    GZFX owned

only when:

    renderer_execution_service::QueryOwnedCommandList(...)

recognizes it.

Everything else is emitted with owner label:

    "skyrim"

Therefore "skyrim" currently means:

    NON-GZFX-REGISTERED / UNKNOWN PROVENANCE

not:

    PROVEN VANILLA SKYRIM OWNER.

The dominant list also executes after the current UiPresent stage timestamp
under the same frame label.

Current renderer_forensics HookPresent sequence is:

    hook receives Present
    ->
    GZFX OnPresent callbacks
    ->
    semantic/resource/effect/telemetry work
    ->
    frame counter reset/increment
    ->
    original DXGI Present

The current UiPresent semantic event is therefore not sufficient by itself to
mean:

    "all renderer work for this frame is complete and DXGI Present is now the
    next API action."

The dominant list could be:

    late engine work
    work performed during a GZFX Present callback but not registered with the
    ownership service
    another in-process graphics subsystem
    work whose logical frame differs from the current integer frame label.

The field evidence proves execution order.

It does NOT yet prove logical ownership.

Required correction:

    rename or reinterpret the "skyrim" owner category as non-GZFX/unknown
    until provenance is captured.

Required research:

    establish a true frame/present timeline and command-list provenance model.

20. DATA-DRIVEN NEXT RESEARCH QUESTIONS
======================================================================

The research phase must now be deeper than another small detector tweak.

Required topics:

A. Skyrim renderer / frame pipeline
   - What engine-level functions define real end-of-world, post-processing,
     UI and DXGI-present boundaries?
   - Can stable SkyrimSE.exe call sites provide semantic anchors stronger than
     API-shape heuristics?

B. Present timeline
   - What work can legally occur in our current Present hook before the
     original DXGI Present?
   - Which GZFX callbacks execute command lists during that window?
   - Where should a true BeforeDxgiPresent / AfterDxgiPresent boundary live?

C. Command-list provenance
   - How should CreateDeferredContext, FinishCommandList and ExecuteCommandList
     record caller module / return-address / thread identity?
   - Can we prove which lists originate in SkyrimSE.exe versus GZFX.dll or
     another module without expensive per-draw stack walking?

D. ReShade architecture
   - How does current ReShade wrap D3D11 devices, contexts, command lists and
     swap chains?
   - How does it define present/command-list lifecycle events?
   - Which architectural ideas are reusable without copying code?

E. ENB
   - What public evidence exists for the Skyrim SE ENB proxy/interception
     model and render integration?
   - ENB internals are closed source; do not invent them.

F. Community Shaders / CommonLibSSE
   - Which public engine-level Skyrim graphics hooks and named render targets /
     passes have already been reverse engineered?
   - Can those findings guide a SKSE-free signature-scanned engine-anchor
     layer in GZFX?

G. Better detector architecture
   - multi-candidate / restartable graph recognition
   - independent landmark detectors instead of one failed gate suppressing all
     downstream stages
   - per-predicate diagnostic counters
   - structural family graph and per-frame DAG scoring.

H. Better telemetry architecture
   - keep global lightweight evidence
   - always emit compact deferred-list metadata regardless of late-detail gate
   - selectively emit deferred run bodies or structural family IDs
   - do not return to 0.0.24 full-frame CSV volume.
