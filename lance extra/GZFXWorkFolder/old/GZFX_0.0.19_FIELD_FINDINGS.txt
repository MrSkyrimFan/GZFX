13. MAJOR FINDING #1:
AFTER_CAMERAZ SCHEDULER EVENT DOES NOT FIRE
======================================================================

This is a real Wave 2 defect.

The CameraZ resource itself is healthy.

Every manual capture shows:

CAMERAZ
verified
2560x1440
R32_FLOAT
12 mip levels

The raw pipeline independently proves that Skyrim rebuilds all twelve CameraZ
mips every frame.

Each 3-frame manual capture therefore contains:

36 CameraZ mip writes

12 mips x 3 frames

This is true in all 19 captures.

Total CameraZ hierarchy writes across the manual campaign:

684

However:

stage_schedule_manual_0001.csv
through
stage_schedule_manual_0019.csv

contain:

0 after_cameraz events

The automatic stage_schedule.csv also contains:

0 after_cameraz events

This is not because CameraZ failed.

It is because the scheduler event is currently coupled to first semantic
promotion rather than to completion of the hierarchy every frame.

CameraZ was already promoted before the manual evidence windows.

Once the identity was known, later full mip-hierarchy completions updated
CameraZ state but did not produce a new promotion, so the stage signal never
fired.

Architectural consequence:

A future production callback registered at:

AfterCameraZ

would not have a reliable per-frame execution boundary.

This is a foundation blocker for Wave 2.

FIELD VERDICT:
CAMERAZ RESOURCE = PASS
AFTER_CAMERAZ SCHEDULER BOUNDARY = FAIL

Required later engineering direction:

Separate:
"resource was newly promoted"

from:
"the verified CameraZ hierarchy completed this frame"

The latter must be a per-frame semantic stage event.

No code change is authorized by this findings document.
This belongs in the upcoming research / blueprint / implementation cycle.

14. MAJOR FINDING #2:
THE CURRENT "OPAQUE_FINAL_DEPTH" NAME / BOUNDARY IS NOT SAFE
======================================================================

This campaign exposed a deeper depth-chronology problem.

The authority currently classifies:

the first same-shape MAIN_DEPTH CopyResource occurring after opaque MRT activity

as:

OPAQUE_FINAL_DEPTH

and emits:

after_opaque_geometry_final_depth

The field data does NOT support keeping that semantic name without further
research.

DAY / NIGHT EXTERIOR:

There are three MAIN_DEPTH copies per frame family:

1. MAIN_DEPTH -> early depth copy
2. MAIN_HDR -> HDR copy
3. MAIN_DEPTH -> second/later depth copy

The scheduler order is consistently:

after_depth_prepass
then
after_stock_ao
then
lighting composite

after_opaque_geometry_final_depth

Example, daylight capture 0001 frame 2483:

ordinal 4452

ordinal 6988

lighting composite:
ordinal 6990

current "after_opaque_geometry_final_depth":
ordinal 7207


Therefore the resource currently called OPAQUE_FINAL_DEPTH is copied:

AFTER stock AO
AFTER raw-indirect / lighting composition

not before those stages.

That chronology is incompatible with casually treating it as the depth source
that enabled CameraZ / AO / indirect composition earlier in the frame.

INTERIORS MAKE THIS EVEN MORE IMPORTANT.

Every interior frame contains:

MAIN_DEPTH -> early depth copy

but does NOT contain the second/later MAIN_DEPTH copy at all.

Interior copy count:

The missing interior copy is exactly the later MAIN_DEPTH copy.

Yet CameraZ, RawAO, AO filtering, RawIndirect and lighting composite all
continue to run normally indoors.

Therefore:

the second/later exterior depth copy is NOT a universal prerequisite for the
core AO/indirect lighting path.

Current field-safe conclusions:

DEPTH_EARLY_COPY:
real, per-frame, cross-environment

second/later exterior depth copy:
real, but exact semantic role unresolved

Current label:
OPAQUE_FINAL_DEPTH

is now too confident.

Current scheduler boundary:
AfterOpaqueGeometryFinalDepth

is now too confident.

This is not merely naming pedantry.

If production AO/GI were later attached assuming this is the universal
finished opaque depth boundary, interior rendering would immediately violate
the assumption.

FIELD VERDICT:

CURRENT OPAQUE_FINAL_DEPTH SEMANTIC = NOT ACCEPTED

18. SEMANTIC AUTHORITY EVIDENCE SNAPSHOT TIMING
======================================================================

Another diagnostic detail surfaced.

The manual authority files define capture windows such as:

capture_start=4816
capture_end=4818

but several semantic-table rows can report:

last_seen_frame=4819

The authority is always running, and the snapshot is written after the
three-frame evidence window finishes.

Therefore the top semantic table represents the authority's current
session-registry state at write time, which can include the following frame.

By contrast:

capture_promotions:

is correctly bounded to the requested capture frames.

This is not evidence corruption, but the distinction should be explicit.

For future machine analysis, the report should ideally separate:

SESSION AUTHORITY SNAPSHOT

from:

CAPTURE-LOCAL AUTHORITY SNAPSHOT

rather than presenting one table in a way that can be mistaken for strictly
capture-bounded state.

FIELD VERDICT:
CAPTURE PROMOTION LOG = GOOD
TOP AUTHORITY SNAPSHOT = USEFUL BUT NOT STRICTLY CAPTURE-LOCAL

This field test did NOT show that the 0.0.19 foundation was a failed design.

Quite the opposite.

The foundation worked well enough to reveal two deeper architectural facts
that the synthetic harness could not expose:

1. CameraZ resource promotion and CameraZ stage completion are different
   concepts and must be represented separately.

2. Skyrim's depth-copy chronology is environment-dependent and the current
   "first post-MRT depth copy = finished opaque depth" heuristic is too simple.

That is exactly why this XForge-style workflow is valuable.

The right response is NOT to patch immediately.

The right response is:

FIELD FINDINGS
-> RESEARCH
-> BLUEPRINT REVISION
