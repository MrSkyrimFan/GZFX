======================================================================
3. PRIMARY ROOT CAUSE REPAIRED
======================================================================

0.0.21 used:

    SemanticInputView.semanticGeneration

as a hard temporal continuity token for:

    MAIN_DEPTH_CURRENT
    MOTION
    NORMAL_MASK_CURRENT

Semantic Authority generation is intentionally tied to physical backing
identity / authority promotion.

That is correct for:

    COM lifetime
    SRV cache invalidation
    diagnostics
    identity replacement evidence

It is NOT a logical temporal semantic continuity token.

The native normal target is known to ping-pong between valid physical render
targets in ordinary Skyrim rendering.

Therefore the same logical semantic:

    NORMAL_MASK_CURRENT

can have:

    physical resource A
    ->
    physical resource B
    ->
    physical resource A

while preserving:

    format
    dimensions
    stage
    semantic meaning
    current validity

0.0.22 separates those concepts.

4. SEMANTIC CONTRACT TOKENS
======================================================================

Added a stable logical contract token to:

    native_input::SemanticInputView

New member:

    std::uint64_t contractToken

The token is deterministically derived from:

    semantic enum
    D3D11 resource dimension
    width
    height
    mip level count
    array size
    sample count
    sample quality
    native resource format
    production typed SRV format

The token explicitly excludes:

    COM pointer
    canonical resource identity
    Semantic Authority physical generation

Therefore:

same semantic layout on a ping-pong resource
->
same contract token

actual layout / semantic contract change
->
different contract token

The physical semantic generation remains available and continues to drive
native view-cache rebuilding where appropriate.

This is the intended separation:

PHYSICAL IDENTITY
    resource lifetime / SRV cache / evidence

LOGICAL CONTRACT
    temporal continuity

======================================================================
6. IMPORTANT CAMERA-CUT PERFORMANCE DECISION
======================================================================

An implementation experiment briefly considered reading the GPU cut-state
buffer back every frame so CPU history state could label camera-cut resets.

That design was rejected before merge.

Reason:

    a synchronous per-frame GPU -> CPU readback on the render thread would
    damage the very performance architecture Wave 3 exists to establish.

Final design:

    camera-cut rejection stays GPU-native during ordinary frames

Capture-only camera-continuity evidence may read the cut-state buffer because
manual evidence is bounded.

CPU reset-event logging records the renderer/contract lifecycle resets that do
not require a GPU stall.

This is a deliberate correctness/performance boundary, not missing work.

7. CAMERAZ BACKGROUND DIAGNOSTIC FIX
======================================================================

0.0.21 used:

    stockValid =
        isfinite(CameraZ) &&
        CameraZ > 0

as the CameraZ geometry predicate.

The field run proved this was wrong.

Public reconstructed Skyrim CameraZ code clamps reconstructed depth to a
positive far value.

Therefore sky/background can contain positive CameraZ values.

0.0.22 now determines:

    stockFar =
        maximum finite CameraZ mip0 depth

Then:

    epsilon =
        max(
            abs(stockFar) * 1e-5,
            1e-4)

    stockBackground =
        abs(stockDepth - stockFar) <= epsilon

    stockGeometry =
        finite
        && stockDepth > 0
        && !stockBackground

Capture evidence now reports:

    stock_far_value
    stock_far_epsilon
    stock_background_pixels
    stock_geometry_pixels
    common_geometry
    gzfx_only_geometry
    stock_only_geometry
    both_background

Numerical error statistics are calculated only for common geometry.

This removes the 0.0.21 false classification where broad sky/background was
reported as stock-only geometry.

9. HUMAN-DOABLE ARM-THEN-ACT CAPTURE
======================================================================

The 0.0.21 test required the user to:

    move
    + strafe
    + turn camera
    + hold Shift
    + press Numpad5

simultaneously.

That is now explicitly prohibited by project governance.

0.0.22 Wave 3 capture is delayed after the request.

Current production delay:

    30 Wave 3 executions

The intended human workflow is:

    press Shift+Numpad5
    release the capture chord
    return hands to ordinary movement/mouse controls
    perform requested movement
    Wave 3 captures after the bounded delay

If the exact target frame is skipped because the renderer temporarily does not
produce AfterOpaqueWorldMRT, the capture uses the first valid Wave 3 frame at
or after the target.

This prevents a capture from becoming permanently stuck because one exact
frame was unavailable.

======================================================================
10. BLUEPRINT DEVIATION - NO 60-FRAME FULL READBACK WINDOW
======================================================================

Research/blueprint proposed:

    ~15 frame arm delay
    +
    ~60 frame observation window
    +
    select maximum mean-motion frame

The final implementation intentionally uses one delayed representative frame
instead of performing full-resolution motion/debug readbacks for every frame
in a 60-frame window.

Reason:

A 2560x1440 R16G16 motion surface plus debug/history readback across dozens of
frames would introduce a large artificial render-thread synchronization cost
during the exact motion test being measured.

The final implementation preserves the real user requirement:

    capture first
    then move naturally

without introducing repeated full-resolution readback stalls.

This deviation is accepted for 0.0.22 field validation.

If later testing proves one delayed frame insufficient, the correct next
upgrade is a small GPU reduction / asynchronous evidence ring, not sixty
synchronous full-frame CPU readbacks.
