1. EXECUTIVE CONCLUSION
======================================================================

The correct next architecture is NOT another broad anonymous-D3D cartography
pass and NOT a one-line repair to the 0.0.25 HDR state machine.

The 0.0.25 field evidence plus public renderer research now supports a much
stronger model:

    Skyrim engine semantic anchors
    +
    GZFX D3D11 resource/pass telemetry
    +
    explicit GZFX command-list ownership
    +
    explicit DXGI Present timeline

This hybrid model should become the next renderer-cartography authority.

The most important research conclusions are:

1. The core 0.0.25 deferred-context observation model was technically valid
   D3D11 engineering, but the old "Skyrim deferred command-list blind spot"
   was misclassified.

2. A GZFX source audit found direct GZFX command-list execution paths that
   bypass renderer_execution_service ownership tagging. The dominant
   once-per-frame "skyrim" / unknown list is overwhelmingly likely to be
   GZFX visible_pass work, not hidden vanilla Skyrim rendering.

3. The current UiPresent event is not the actual DXGI Present boundary.
   It fires inside GZFX's pre-original-Present callback work. GZFX then runs
   visible_pass, which can create and execute a command list, before the real
   IDXGISwapChain::Present is called.

4. Skyrim's renderer already exposes named engine-level image-space effects
   that correspond directly to the semantic stages GZFX has been inferring:
       HDR downsample / luminance / adaptation
       HDR tonemap variants
       temporal AA
       temporal AA for water
       water blend
       reflection apply
       image copies
       post-processing
       UI/menu draw start

5. Community Shaders demonstrates that these named Skyrim engine stages can be
   observed directly by hooking known engine functions and image-space shader
   vtables, then correlated with D3D11 work.

6. ReShade independently demonstrates the correct API-lifecycle model:
       wrap deferred contexts when created
       observe recording
       close at FinishCommandList
       execute secondary command lists explicitly
       distinguish present-entry from post-present/finish-present.

7. ENB provides useful high-level evidence that a mature Skyrim graphics
   framework must own both graphics interception and engine/post-processing
   integration, but current Skyrim SE ENB internals are proprietary and must
   NOT be reverse-copied or assumed.

8. GZFX can implement the useful engine-anchor ideas while remaining fully
   SKSE-free. The project already links MinHook v1.3.4. What is missing is a
   small fail-closed SkyrimSE.exe anchor resolver, not a new hook library.

9. The 0.0.25 greedy HDR detector should be retired as primary semantic
   authority. Structural D3D inference should remain as independent evidence
   and fallback, but named engine anchors should become the primary
   late-renderer semantic source where available.

10. The next coherent engineering wave should fix ownership/timeline truth
    first, add a small set of verified engine anchors second, correlate those
    anchors with the existing D3D telemetry third, and only then promote
    WaterDomain / HDR / TAA / PostTonemapPreUi.

This is a materially better path than trying to infer the entire Skyrim
renderer forever from anonymous texture dimensions and shader pointers.

    owner=skyrim

4. MICROSOFT D3D11 FACTS
======================================================================

Microsoft documentation confirms that the original 0.0.25 observation
architecture is valid:

- ID3D11Device::CreateDeferredContext creates a deferred context that records
  commands into command lists.

- Multiple deferred contexts may exist.

- FinishCommandList produces the ID3D11CommandList.

- ExecuteCommandList on the immediate context is required to execute recorded
  commands on the GPU.

- Executing a command list on another deferred context can merge lists.

- ID3D11CommandList itself exposes no API for enumerating its recorded draws
  and dispatches after creation. Its public command-list-specific method is
  GetContextFlags.

Therefore:

    observe while deferred context records
    ->
    seal our own record at FinishCommandList
    ->
    join at ExecuteCommandList

remains the correct D3D11 strategy whenever true external deferred work exists.

Microsoft also documents:

    CreateDeferredContext1
    CreateDeferredContext2
    CreateDeferredContext3

on newer device interfaces.

ReShade wraps all of these, not only the base method.

Research implication:

    base CreateDeferredContext coverage was sufficient for the current field
    evidence, but production-grade compatibility should eventually cover the
    interface-version variants if evidence shows they are used.

This is NOT the current primary blocker.

Primary blocker is semantic/timeline truth.

5. RESHADE ARCHITECTURE — REUSABLE FACTS
======================================================================

ReShade is a useful public architectural reference because it solves the same
general API-observation problem without needing game-specific semantics.

Current ReShade D3D11 code:

    source/d3d11/d3d11_device.cpp

wraps:

    CreateDeferredContext
    CreateDeferredContext1
    CreateDeferredContext2
    CreateDeferredContext3

and returns a proxy D3D11DeviceContext around the original context.

Current:

    source/d3d11/d3d11_device_context.cpp

treats command-list lifecycle explicitly.

FinishCommandList:

    closes the recorded command list
    creates/wraps the command-list object
    emits add-on lifecycle events.

ExecuteCommandList:

    recognizes secondary command-list execution
    invokes lifecycle events
    calls the underlying runtime
    restores/emits default-state behavior when necessary.

ReShade also distinguishes present lifecycle events rather than using one
ambiguous "present" concept.

Recent public ReShade changes are especially relevant:

- a finish_present event exists after successful presentation;
- D3D11 deferred-event behavior has received explicit fixes;
- ExecuteCommandList without restore-state causes default-state event handling;
- older changes distinguish command-list execution/flush behavior that may be
  implicit around presentation.

Research lesson for GZFX:

A. Every command list needs explicit lifecycle identity.

B. Every command list needs explicit provenance.

C. Present needs explicit phases:
       entry
       GZFX pre-original work
       immediately before original DXGI call
       return/success

D. State restoration must be modeled as an API fact, not guessed from later
   bindings.

GZFX does NOT need to copy ReShade.

Its public architecture simply validates the lifecycle model.

ReShade source:

https://github.com/crosire/reshade/blob/main/source/d3d11/d3d11_device.cpp

13. DXGI PRESENT TIMELINE:
REPLACE ONE AMBIGUOUS MARKER WITH EXPLICIT EPOCHS
======================================================================

Current GZFX naming conflates an internal semantic event with actual
presentation.

The next architecture should add explicit present phases.

Recommended telemetry events:

    PresentHookEnter
        first instruction of GZFX IDXGISwapChain::Present detour

    PresentCallbacksBegin

    PresentCallbackSemanticProbeBegin/End
    PresentCallbackResourceIntelligenceBegin/End
    PresentCallbackSemanticAuthorityBegin/End
    PresentCallbackVisiblePassBegin/End
    PresentCallbackTelemetryBegin/End

    BeforeOriginalDxgiPresent
        immediately before calling the original swap-chain Present

    AfterOriginalDxgiPresent
        immediately after original returns

    PresentResult
        HRESULT / flags / sync interval

Do not call any of these UiPresent unless they actually refer to UI.

Keep:

    engine UI start

as a separate semantic event.

The existing integer frame number should not be the only temporal coordinate.

Add a monotonically increasing:

    present_epoch

and keep QPC on every event.

A command list should therefore be locatable as:

    engine frame
    present epoch
    callback phase
    D3D ordinal
    thread
    caller module.

This removes the ambiguity that caused the 0.0.24/0.0.25 deferred
misclassification.

16. SKSE-FREE ENGINE ANCHOR RESOLUTION
======================================================================

GZFX must remain:

    SKSE-free.

Community Shaders/CommonLib use Address Library relocations because they are
SKSE ecosystem projects.

That mechanism should NOT be imported as a runtime dependency.

GZFX already links:

    MinHook v1.3.4

through root CMakeLists.txt.

Therefore the missing production piece is only:

    Skyrim engine address resolution.

Recommended standalone resolver design:

A. Runtime fingerprint.

Record:

    SkyrimSE.exe product/file version
    PE timestamp
    image size
    .text section size
    optional bounded .text hash/fingerprint.

B. Version-aware signatures.

Maintain a small table for only the required engine anchors.

Use byte signatures with wildcards around relocations and call targets.

C. Decode target.

For a callsite anchor:

    locate signature
    validate opcode
    decode relative call target
    validate target in SkyrimSE.exe executable section.

D. Multi-factor validation.

For each anchor require several of:

    expected section
    expected nearby instruction shape
    expected call target range
    expected referenced RTTI/string/vtable relationship
    unique match
    expected function prologue / control-flow properties.

E. Fail closed.

If an anchor has:

    zero matches
    multiple matches
    failed validation
    unexpected pre-existing patch state

then:

    do not hook it
    log unavailable
    retain D3D fallback evidence.

F. Record evidence.

Write:

    engine_anchors.csv

with:

    anchor name
    resolver method
    runtime fingerprint
    resolved RVA
    validation status
    call count
    conflict state.

Absolute runtime addresses are evidence only.

They are NOT renderer contracts.

17. RTTI / VTABLE RESOLUTION AS A SECONDARY OPTION
======================================================================

For polymorphic BSImagespaceShader classes, MSVC RTTI gives a second possible
SKSE-free resolution lane.

Candidate strategy:

    locate the SkyrimSE.exe RTTI/type descriptor for a named class
    ->
    identify its Complete Object Locator / vtable relationship
    ->
    validate vtable function entries point into executable SkyrimSE.exe code
    ->
    hook only the required Render/Dispatch slot.

Advantages:

    semantic class identity
    no dependency on field shader pointers
    often more stable than a raw absolute address.

Risks:

    compiler/runtime layout differences
    inheritance complexity
    vtable hook collisions with other graphics mods
    more resolver engineering than a simple callsite.

Research recommendation:

    use signature-scanned engine callsites/functions as the primary first
    implementation;

    use RTTI/vtable discovery as:
        independent validation
        or for named image-space effects that lack a cleaner central callsite.

Do not build a giant generic RTTI framework before a real need exists.

detour the same engine function heads, causing immediate crashes if both write
over the same prologue.

This is highly relevant to a future public GZFX.

Therefore engine-anchor hooking must include conflict awareness.

Recommendations:

1. Prefer a stable callsite hook over a shared function-head hook when one
   specific callsite is all GZFX needs.

2. Before applying a MinHook detour or callsite patch:
       verify expected bytes/signature;
       detect whether target is already patched.

3. If an unknown pre-existing detour is found:
       fail closed for that anchor;
       log conflict;
       continue with D3D fallback.

4. Do not blindly overwrite another framework's trampoline.

5. Vtable hooks should preserve and call the currently installed previous
   function pointer when safe, but GZFX should still record that a chain was
   detected.

6. Later compatibility work can deliberately support known frameworks, but
   cartography must first remain deterministic in the user's current clean
   field environment.

However:

    current ENB Skyrim SE internals are proprietary.

technical extraction and unauthorized reuse.

Therefore GZFX research policy must be:

    read official public behavior/docs
    observe interoperability from our own runtime
    do NOT decompile/copy proprietary implementation
    do NOT invent undocumented internal hook details.

ENB is useful as proof of architecture class, not as code to reproduce.

22. BETTER STRUCTURAL FALLBACK DETECTOR
======================================================================

Even after engine semantic anchors exist, structural D3D detection remains
valuable for:

    independent validation
    compatibility fallback
    detecting modded/replaced paths
    proving resource identity.

The HDR fallback must be redesigned.

Do NOT:

    latch first candidate forever.

Use a candidate graph.

Per frame:

1. Start a candidate whenever a qualifying MAIN_HDR-descendant RGBA16F
   downsample appears after the correct engine/postprocessing epoch.

2. Maintain several bounded candidates simultaneously.

3. Extend a candidate only when:
       output dimensions descend
       dependency consumes previous candidate output
       format/domain remains coherent.

4. Allow replacement / restart.

5. Expire stale candidates after:
       bounded ordinal distance
       leaving postprocessing epoch
       contradictory growth/path.

6. Commit HDRReduction only when a candidate reaches:
       tiny terminal target <=4x4
   AND downstream evidence supports:
       adaptation descendant
       full-resolution tonemap/current output.

7. Score the full graph, not the first edge.

This prevents the exact 0.0.25 poisoning failure.

23. INDEPENDENT TAA FALLBACK
======================================================================

TAA fallback should not be hard-gated on the HDR detector.

The 0.0.25 architecture had:

    failed HDR
    ->
    no tonemap
    ->
    no TAA eligibility

even though the TAA structure itself was obvious.

New fallback rule:

Global TAA candidate can be recognized independently when:

    within verified Skyrim postprocessing epoch
    reads MOTION
    reads MAIN_DEPTH_CURRENT
    reads current/history full-resolution color
    writes two full-resolution temporal outputs.

If engine ISTemporalAA anchor exists:

    engine event + D3D structure must correlate.

If engine anchor is unavailable:

    structural detector can report:
        high-confidence candidate

but stage promotion remains provisional until acceptance rules are met.

This prevents one upstream detector defect from blacking out all downstream
cartography.

33. FINAL RESEARCH VERDICT
======================================================================

The 0.0.25 field test did not close late-stack cartography, but it exposed a
better route and removed a false blocker.

Most important correction:

    the dominant "Skyrim" deferred command list is very likely GZFX's own
    untagged visible-pass work.

Most important architecture discovery:

    Skyrim exposes named engine-level post-processing, HDR, temporal, water,
    copy, world, shadow, and UI landmarks that can be correlated directly
    with GZFX's already-proven D3D telemetry.

Therefore the project should stop trying to make anonymous D3D inference carry
the entire semantic burden.

Recommended model:

    ENGINE SEMANTICS
        tell us WHAT Skyrim says it is doing

    D3D TELEMETRY
        tells us WHAT resources/passes actually execute

    OWNERSHIP / PROVENANCE
        tells us WHO issued the work

    PRESENT TIMELINE
        tells us WHEN the work occurs relative to real presentation

When all four agree, a renderer boundary can be locked with much higher
confidence and dramatically less telemetry.
