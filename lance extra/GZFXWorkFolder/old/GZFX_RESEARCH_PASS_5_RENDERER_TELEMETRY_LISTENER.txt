    understand Skyrim's full rendering pipeline

2. RESEARCH VERDICT
======================================================================

Build a dedicated:

    GZFX Renderer Telemetry Listener

Target runtime:

    0.0.24-renderer-telemetry-listener

The listener is NOT another screenshot/capture subsystem.

It is a continuous session recorder.

The user should be able to:

    launch Skyrim
    play normally
    cycle Mode 0/1/2/3/4
    move between interiors/exteriors
    change time day/night
    visit water/reflection/weather-heavy scenes
    move camera/player naturally
    quit Skyrim
    ZIP one TelemetrySession directory
    upload it

The listener should continuously preserve enough renderer evidence that
Project Chat can reconstruct what happened without requiring the user to press
a capture key at exactly the right moment.

======================================================================
3. WHY THE CURRENT MANUAL CAPTURE SYSTEM IS NO LONGER ENOUGH
======================================================================

The manual system was valuable for proving Waves 1-4.

It now has structural limitations for full-stack discovery:

- evidence only exists around requested windows;
- manual operator timing influences what gets sampled;
- one pending Wave4 capture can swallow a later request;
- hundreds of BMPs make evidence large;
- visual captures are expensive and can perturb timing;
- pipeline discoveries between manual windows are invisible;
- mode/day/night/interior transitions must be choreographed by the user;
- broad architecture work now needs session continuity, not isolated snapshots.

Manual screenshots remain useful for later visual-quality gates.

They should stop being the primary renderer-discovery instrument.

======================================================================
4. D3D11 THREADING CONSTRAINT
======================================================================

Microsoft's D3D11 threading model is clear:

    the immediate context should be used by one thread at a time.

DXGI/Present should also remain on that same rendering thread.

Therefore the telemetry writer thread MUST NOT:

- call the Skyrim immediate D3D11 context;
- call Present;
- query live D3D state through immediate-context getters;
- map renderer-owned GPU resources;
- resolve GPU queries itself.

The render thread captures only CPU-side metadata into fixed-size records.

The writer thread performs only:

- queue draining;
- text formatting;
- file writes;
- log rotation;
- manifest/status maintenance.

This avoids enabling ID3D11Multithread globally, which Microsoft documents as
adding per-call overhead.

======================================================================
5. RENDER-THREAD COST MODEL
======================================================================

The listener must avoid:

    fprintf/ofstream per draw
    heap allocation per draw
    std::string construction per draw
    COM AddRef/QueryInterface per event
    large mutex-protected vector growth
    GPU readback
    synchronous FlushFileBuffers
    D3D state getters

inside hot renderer hooks.

Render-thread work should be bounded to:

    copy fixed-size POD record
    atomic ring reservation/commit
    optional cheap hash/compare
    increment counters

No disk I/O occurs in draw/dispatch hooks.

======================================================================
6. EVENT QUEUE
======================================================================

Use a preallocated bounded lock-free ring.

Recommended initial capacity:

    262,144 events

Fixed-size event record:

    approximately 96-128 bytes

Memory budget:

    roughly 24-32 MiB

This is acceptable for a forensic build.

Use monotonic sequence numbers.

Queue overflow MUST NOT block Skyrim.

If full:

    drop event
    increment dropped counter
    preserve listener health status

Never stall the render thread waiting for the writer.

======================================================================
7. EVENT COMPRESSION
======================================================================

Logging every draw call verbatim can create hundreds of thousands of records
per second.

Full-stack discovery does not require 500 identical adjacent records.

Use render-thread run compression for pipeline pass events.

A pass-family signature should include:

    pass kind
    VS/HS/DS/GS/PS/CS shader hashes
    RTV identities
    DSV identity
    OM/CS UAV identities
    viewport width/height
    topology
    blend/depth/raster state hashes
    compact read-resource hash
    compact write-resource hash
    constant-buffer binding hash
    sampler binding hash

Adjacent pass events with the same family signature can become:

    first ordinal
    last ordinal
    repeat count

When the signature changes:

    publish previous run to telemetry ring
    start new run

This preserves renderer order and pass-family structure while reducing volume.

Exact draw arguments are not needed for every repeated geometry draw.

Retain first/last arguments or aggregate vertex/index/instance counts where
useful.

For each semantic:

    identity

======================================================================
17. TIMINGS.CSV
======================================================================

The listener should centralize already-resolved CPU/GPU timing metadata.

Do not perform new GPU GetData calls from the writer thread.

Wave3/Wave4 continue resolving their own asynchronous timestamp queries on the
render thread with DONOTFLUSH behavior.

Expose timing snapshots through small CPU-only getters.

Record:

    frame
    Wave3 total/components
    Wave4 total/components
    future feature timings
    timing valid bits

Current Microsoft guidance confirms DONOTFLUSH prevents forced command-buffer
flushes, so timing should remain asynchronous.

======================================================================
18. PIPELINE CARTOGRAPHY EXTENSION
======================================================================

Do not duplicate the existing D3D state tracker.

Extend Pipeline Cartography with a continuous telemetry sink.

Current issue:

    state tracking and PassRecord construction only run while a manual
    capture window is active.

Required model:

    manualCaptureActive
    OR
    telemetrySinkActive
    ->
    track current pipeline state.

When manual capture is active:

    preserve existing full PassRecord behavior.

When telemetry is active:

    construct only compact PassTelemetry POD.

Do not push full vectors/access lists into the listener.

Pipeline Cartography remains the source of truth for:

    shader hashes
    resource identities
    state hashes
    resource metadata.

======================================================================
19. TELEMETRY CALLBACK CONTRACT
======================================================================

Add to Pipeline Cartography:

    SetTelemetrySink(...)
    ClearTelemetrySink(...)

Callbacks for:

    compact pass event
    resource discovery/update

Callback MUST happen outside Pipeline Cartography's internal mutex.

Reason:

    listener enqueue may trigger unrelated atomics/event signaling and should
    not nest inside cartography lock ownership.

Build the POD under the lock.

Copy it.

Unlock.

Invoke callback.

======================================================================
20. STAGE SCHEDULER INTEGRATION
======================================================================

Telemetry Listener registers a callback for every Stage Scheduler Boundary.

No Stage Scheduler code duplication.

Current callback invocation already occurs after the scheduler releases its
internal mutex.

This is safe for a tiny telemetry enqueue.

======================================================================
21. SEMANTIC AUTHORITY INTEGRATION
======================================================================

At Present/end-of-frame:

    GetSnapshot()

Compare against prior listener snapshot.

No disk writing inside Semantic Authority.

No new semantic inference inside the listener.

Listener records what Semantic Authority believes plus changes over time.

This preserves the authority boundary.

23. RENDERER FORENSICS INTEGRATION
======================================================================

Renderer Forensics already owns the primary Present/frame lifecycle.

At OnPresent:

    gather frame counters
    semantic snapshot
    Wave3 status
    Wave4 status
    execution generations
    current development mode

then call:

    telemetry_listener::OnPresent(...)

The listener should own frame/QPC bookkeeping and enqueue the frame record.

    HookExecuteCommandList

Notify ownership telemetry there.

======================================================================
24. MODE CHANGES
======================================================================

No special input-hook integration is required.

The listener reads:

    state::GetDevelopmentMode()

each frame.

When value differs from previous frame:

    emit transition=mode_change

This also captures any future programmatic setting change.

======================================================================
25. ENVIRONMENT / DAY-NIGHT
======================================================================

Environment:

    use Semantic Authority EnvironmentClass.

Day/night:

Skyrim's current renderer map does not yet expose a canonical semantic called
"day/night."

Do NOT guess from clock values that GZFX does not own yet.

The user can produce day/night sessions naturally.

The listener can distinguish their renderer behavior from:

    shader/pass/resource/timing changes

even before a named time-of-day semantic exists.

If research later identifies a stable current weather/time constant-buffer
field, promote it through evidence, not assumption.

======================================================================
27. WRITER THREAD
======================================================================

Create one dedicated telemetry writer thread.

Startup:

    after RuntimeRoot/DiagnosticsRoot exist
    before normal gameplay session begins

Shutdown:

    process detach best effort
    explicit Stop from runtime where possible

Writer loop:

    wait up to ~250 ms
    drain events in large batches
    format CSV rows into a large memory buffer
    append to current segment files
    flush standard stream buffers approximately once per second
    update listener_status.txt

No FlushFileBuffers per event.

No render-thread joins.

======================================================================
28. FILE ROTATION
======================================================================

Pipeline data can become large.

Use segmented logs.

Recommended segment size:

    64 MiB

When a pipeline segment exceeds limit:

    close
    increment segment index
    open next file with header

Keep all segments for the session.

Do not delete older segments automatically during a user-requested forensic
session.

The user will upload one TelemetrySession ZIP after testing.

For extremely long sessions, a configurable total cap can be added later.

======================================================================

At listener start create:

    GZFX/TelemetrySession/

If an old session exists:

    move/rename to:
        TelemetrySession_previous

or:

    create timestamped session:
        TelemetrySession_YYYYMMDD_HHMMSS

Timestamped session directory is preferred.

Write:

    x-style completion marker equivalent:
        telemetry_session_complete.txt

on clean shutdown / process detach when possible.

If missing after crash:

    session is still analyzable
    but marked unclean.

35. WHAT THE NEXT DATA PASS SHOULD ANSWER
======================================================================

The first listener session should allow Project Chat to answer:

- which pass families are stable across all environments?
- which pass families are exterior-only/interior-only?
- which resource identities ping-pong?
- where do water/reflection resources appear and get consumed?

- what resources feed HDR reduction/exposure?

- how modes change GZFX-owned passes vs Skyrim passes?
- which currently-unmapped resources have stable producer/consumer signatures?
- which domains still require targeted capture/probing?

This is the correct route to full-stack ownership.

36. RESEARCH CONCLUSION
======================================================================

The owner proposal is accepted.

The project should stop using isolated manual capture windows as its primary
renderer-discovery mechanism.

Build an always-on, asynchronous, structured telemetry listener inside
GZFX.dll.

The listener should reuse:

    Pipeline Cartography
    Semantic Authority
    Stage Scheduler
    Renderer Execution Service
    Wave3/Wave4 status

and convert them into one continuous session record.

This brings Project Chat materially closer to Codex-style live forensic
visibility while respecting the actual limitation that Project Chat reviews
the session after upload rather than watching it live.
